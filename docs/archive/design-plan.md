# NKD — Upfront Design Plan

> [!CAUTION]
> **Historical implementation plan.** This document preserves the original target architecture, sequencing,
> and proposed interfaces. Completion markers and examples are not current support or acceptance claims. The
> proposed ADRs in `docs/adr/` are the maintained engineering baseline pending ratification;
> `docs/adr/reconciliation.md` records what is implemented, deliberately disabled, and still operationally
> unproven, including the remediation order actually followed.

**Companion to** [`docs/epics.md`](epics.md) (the SRD → Epic backlog) and the target [`docs/nkd-srd-doc.md`](nkd-srd-doc.md).
**Purpose:** the backlog says *what* to build; this plan captures the **design work that must be settled before —
or in the first sprint of — implementation**, because it is *shared across many Epics*, *hard to reverse once
code/bytes ship*, *not-yet-decided/non-normative*, or a *technical risk that must be proven by a spike*.

> Produced by a design-focused multi-agent pass: one agent per design domain (grounded against `docs/epics.md`
> and the code) extracted the upfront decisions and sketched concrete recommendations, then two adversarial
> critics (sequencing/gating, completeness/overlap) reconciled them. Their fixes are folded in: the sprint-0
> set below is the reconciled gating set, §3 resolves the exit-code collisions they found, and §4 assigns a
> single owner to each primitive that was authored in two places.

**What is NOT here:** ordinary implementation tasks — those live in the story acceptance criteria in
`docs/epics.md`. This plan is decisions, schemas, interfaces, invariants, and spikes only.

**54 design decisions across 8 domains** (A–H), each an ADR / schema / invariant / spike / migration / policy.
The critical insight from sequencing: a small **sprint-0 freeze set** gates the entire critical path
(`E0 contracts → E1 → E2 → E5-S1 executed cosign → E6 verify`); everything else fans out from it.

## 1. The gating principle

Design a thing upfront **only** if it is one of:
1. a **shared** schema/interface many Epics reference (deciding it late forces cross-Epic rework);
2. **hard to reverse** once code or signed bytes ship (on-disk/wire schemas, identity models, the exit-code
   contract, the IR-purity boundary, package topology);
3. **not-decided / non-normative** and blocking dependents (ValidationVector, ReleaseSet, NKE inventory,
   the offline bundle format);
4. a genuine **technical risk** that must be *proven by a spike* before an approach is committed.

Two foundations recur and must be honored by every decision:
- **The IR-purity boundary (DD-A2 + DD-C4).** `recipeDigest = sha256(deterministic IR)` is a pure function of
  *resolved catalog inputs only*. No host/clock-from-host/random/UUID/builder-profile/CI-engine/observation
  value may enter the IR. A clock value *derived from a pin* (`SOURCE_DATE_EPOCH` = committer `%ct`) is a
  deterministic catalog input and belongs in the IR; the host wall clock does not. **`recipeDigest` is already
  shipped as `f08265d2…` on the `sigs.k8s.io/yaml` marshaler — that codec is grandfathered and frozen; all NEW
  trust objects use the canonical codec (DD-A1).**
- **One canonical codec + digest-addressing (DD-A1).** Every *new* trust object serializes and hashes through a
  single RFC-8785-JCS-style `pkg/nkd/canonical` package with a per-kind domain tag, so an auditor in any language
  can recompute a digest and a vector digest can never be substituted for a manifest digest.

## 3. The reconciled exit-code table (resolves the flagged collisions)

Both critics flagged live numeric collisions across independently-authored DDs (slot 19 claimed by
`CodeSignatureInvalid` **and** `CodeUntrustedProfile`; slot 24 by `CodeTrustPolicyMissing` **and**
`CodeEncryptedArtifact`; the `30-39` retryable band overlapping the `30-45` release block). Because *codes never
change meaning*, they must be laid out **once**, banded, before any new code ships. Reconciled proposal
(exact integers are ratifiable — the load-bearing contract is *distinctness + banding + stability*):

| Band | Code → exit | Meaning |
|---|---|---|
| **Semantic (non-error)** | `success`=0 · `internal`=1 · `usage`=2 · `diff-differs`=3 | 3 is a documented non-error "differences present" status for `diff` |
| **10–19 resolve / input / crypto** | NoMatch 10 · Ambiguous 11 · ReservedAxis 12 · Unsupported 13 · InvalidCatalog 14 · UnpinnedSource 15 · TagToolchain 16 · PreflightFailed 17 · VariantRejected 18 · **SignatureInvalid 19** | existing 10–18 kept; 19 = crypto did not verify |
| **20–29 build / verify / trust-policy / disk** | FetchFailed 20 · BuildFailed 21 · VerifyFailed 22 · **UntrustedSigner 23** · **TrustPolicyMissing 24** · **UntrustedProfile 25** · **EncryptedArtifact 26** · **EnvelopeDecode 27** | 22 stays strictly for recipeDigest/profile/component/RAW-block divergence |
| **30–31 retryable (transient)** | **Unavailable 30** · **Timeout 31** (32–39 reserved) | lets a CI gate distinguish transient from input errors (INT-051) |
| **40–52 release / lifecycle** | VectorUnpinned 41 · ReleaseIncomplete 42 · GateUnmet 43 · UnverifiedRef 44 · CompatMismatch 45 · ProvenanceMissing 46 · InventoryUnpinned 47 · ImmutableViolation 48 · Withdrawn 49 · UnpinnedInput 50 · MirrorMismatch 51 | one contiguous, non-overlapping block |

Guarded by a golden snapshot test (every `Code` appears once, all statuses pairwise-distinct, none in the POSIX
128+signal range) plus an audit test that every I/O/subprocess/serialization-boundary error is a typed
`*errors.Error` (never bare `fmt.Errorf`), so `ExitCode` never silently degrades to 1.

## 5. Gap decisions — upfront design the backlog needs but no DD owned

The completeness critic found these missing; assign an owner in sprint-0 even where the full build lands later,
because they constrain the E0 schemas:

- **G-1 · Consolidated threat model / trust boundary (STRIDE-style, maps all 17 SEC reqs).** Point defenses
  exist (DD-B2 fail-open, DD-H7 withdraw-DoS, DD-B3 codes) but no single artifact enumerates the adversaries the
  zero-binary claim implies: malicious catalog author, malicious overlay override, compromised mirror/registry,
  replay/rollback of a withdrawn publication, signer-identity spoofing, trusted-root substitution in airgap.
  *Owner:* a new `docs/security/threat-model.md`, E0. **This is the canonical upfront security artifact.**
- **G-2 · Trusted-time / expiry-evaluation authority.** Variant `Expiry` and status `EffectiveEpoch` are
  correctly operator-supplied inputs, but nothing decides *how* "expired"/"withdrawn-as-of" is **evaluated** at
  verify/consume time — which clock, what skew, and the airgap case with no Rekor signed timestamp. Without it,
  E7's expiring variant and E11 status enforcement are unenforceable or silently trust the host wall-clock
  (a SEC-14/SEC-15 hole). *Owner:* an ADR, gates DD-A6/DD-H7/E7/E9.
- **G-3 · `recipeDigest`-stability regression golden.** The one golden that must never move: a CI test asserting
  that adding ValidationVector/ReleaseSet/status/provenance/canonical objects *can never* perturb the shipped
  `f08265d2`, plus the rule that any IR schema change is a deliberate, breaking `recipeDigest` bump. Load-bearing
  because DD-A1 introduces a second codec next to the grandfathered IR marshaler. *Owner:* E0/E1.
- **G-4 · Signer key lifecycle — rotation, revocation, trusted-root update propagation (esp. offline).**
  DD-B2 pins a signer set and DD-B4 pins a trusted-root snapshot, but nothing decides how a compromised/rotated
  identity is revoked or how trust-store/root updates reach an airgapped operator. *Owner:* an ADR cross-cutting
  E5/E6/E9.
- **G-5 · Concurrency / atomicity for on-disk trust state.** The append-only ledger (DD-A6), the mirror store
  (DD-H1), and lock writes need file-locking / atomic-append / idempotent-republish / torn-write semantics.
  DD-G3 covers atomic rename for *build outputs* only; E11's immutability depends on the ledger never being
  racily appended. *Owner:* folded into DD-A6 + DD-H1.
- **G-6 · Deprecation & compatibility policy for NON-hashed surfaces.** DD-A3 governs additive migration for
  *hashed trust* objects only; the SDK (`client/v1`) API, CLI flag/output contract, and the catalog **authoring**
  schema need stability windows + deprecation guarantees before E14/E1 stabilize them. *Owner:* an ADR with DD-G2/G4.
- **G-7 · The SEC-09/10/11 IR-placement questions.** (a) SEC-09: the secret-shaped-key denylist on the `-e`
  allowlist + the artifact/log/SBOM/CI-YAML secret-scan contract. (b) SEC-11: *where* least-privilege container
  flags (`--cap-drop=ALL`/`no-new-privileges`/non-root/read-only-rootfs) live, whether they enter `recipeDigest`
  (an IR-purity/DD-A2 question), and how all four emitters lower them byte-identically. (c) SEC-10: whether the
  network-fetched vendored module set is hashed into `recipeDigest` or a lock (trust-coverage, distinct from the
  DD-H2 *reproducibility* spike). *Owner:* fold (a)/(b) into DD-A2's table + E2; (c) into DD-H2's outcome.
- **G-8 · FR-05 argv-identity proof + emitted-CI-YAML validation.** The *mechanism* to structurally prove each
  adapter's emitted build argv equals the local runner's argv (E2-S1's core claim), and how emitted CI YAML is
  schema/lint-validated. *Owner:* E2.

## 6. Parallel spikes (run DURING sprint-0 — retire gating risk earliest)

These prove technical risks whose outcome *reshapes* a sprint-0 schema, so start them immediately, not in their
tagged phase:

| Spike | Proves | Reshapes if it fails |
|---|---|---|
| **DD-C6** two-machine bake-off | Two physically-distinct machines reproduce the hard lanes (runc CGO/etcd/kubectl) bit-identically | A diverging field graduates to hard-fail (DD-C3) and shrinks the reproducible set + reshapes the DD-C1 tuple. **CLAUDE.md's mandated #1 risk — do not defer.** |
| **DD-H2** vendored-tree reproducibility | `go mod vendor` for etcd/coredns/helm is byte-identical across environments → pin-time vendoring folds into `treeHash` | If not, vendored tree becomes a separate content-addressed input and the source-pin schema + `recipeDigest` change (touches E11). |
| **DD-D3** qemu-img decode determinism | `qemu-img convert -O raw` (decode) is byte-stable across versions for qcow2/vmdk/vhd (convert need NOT be) | Narrows the supported envelope set and pins `ToolDigest` before DD-D1 granularity freezes. |
| **DD-D5** ext4 full-rootfs residual | The ~969-block inode-table residual can be *eliminated* (e.g. Apache-2.0 `tar2ext4`) vs *bounded-and-masked* | If only bounded, DD-D1 must carry `MaskedRegions` and the FR-14 claim degrades to "identical outside a declared region." |
| **DD-G3** cancel-cleanup | A mid-run cancel leaves zero orphaned `nkd-*` containers and zero `.tmp` output dirs | Confirms the container-naming registry + atomic-rename protocol before the scheduler is committed. |

Later spikes (not sprint-0): **DD-B4** offline bundle format (phase-1), **DD-F6** vuln-report determinism (phase-2).

### Domain A — Trust Contracts & Data Model

This domain owns the shared, digest-addressable trust objects that the entire E4/E5/E6/E7/E11/E12 cluster cross-references — the expected-digests Manifest, EvidenceBundle, the VerifyAgainst/Check seam, plus four still-greenfield objects (first-class ValidationVector, atomic ReleaseSet, NKE Inventory, and the signed status-declaration/ledger). Its correctness hinges on three decisions that are hard-to-reverse once bytes are published: one canonical serialization+digest codec, a strict partition of which fields may enter recipeDigest-covered vs signed-manifest vs detached-non-covered bytes, and an additive-only schemaVersion migration discipline so the ValidationVectorRef string->object and single->per-artifact evolutions never perturb covered bytes or churn recipeDigest. Today the codec is already inconsistent (IR/profile use sigs.k8s.io/yaml; attest/evidence use json.MarshalIndent), attest.Manifest has no Digest() at all, and half the objects the SRD worked examples 5.2/5.5/5.7 describe are marked non-normative — so these must be settled in E0 before Phase-2 dependents start. The opinionated through-line: freeze one JCS-style canonical codec for all NEW trust objects, grandfather recipeDigest's YAML, and reserve the full coded-error/exit-code table upfront.

**Package topology.** New pkg/nkd/canonical (E0-owned: the single canonical byte codec + DigestAddressable interface + domain-tagged Digest helper). New pkg/nkd/release (E12: ValidationVector, ReleaseSet, Inventory, Gate, Clearance, Selection). New pkg/nkd/status (E11: StatusDeclaration + append-only publication ledger + publicationIdentity). Extended pkg/nkd/errors (frozen Code->exit-status registry with reserved bands). pkg/nkd/attest changes: add Manifest.Digest(); keep ValidationVectorRef as string=content-digest (+ optional sibling locator), route Marshal through canonical. pkg/nkd/ir/marshal.go grandfathered — recipeDigest stays on sigs.k8s.io/yaml, documented as the one codec exception (changing it would rewrite the shipped f08265d2 digest).

#### DD-A1 — One canonical serialization codec + a DigestAddressable seam for every trust object
`interface · phase: sprint-0`

> **Critic note:** KEYSTONE — author first; every digest-addressable object depends on it. recipeDigest stays grandfathered on sigs.k8s.io/yaml (the one documented codec exception).

- **Question.** What single byte-format and digest interface do all trust objects (Manifest, EvidenceBundle, ValidationVector, ReleaseSet, Inventory, StatusDeclaration, ledger) serialize/hash through, and how do we avoid the current split where IR/profile use sigs.k8s.io/yaml while attest/evidence use json.MarshalIndent — with attest.Manifest carrying no Digest() at all?
- **Why upfront.** Every digest-addressing story (E5-S6, E11-S4 publication identity, E12-S1 vector digest, E12-S2 set digest, E7 variant identity, E8 aggregate release evidence) computes sha256 over these bytes. Once a publisher ships a signed manifest or a ledger entry, the exact byte form is frozen forever — a later codec 'unification' silently rewrites every published identity. Deciding this after E5/E11 land forces re-hashing every trust object. It is also required so an auditor in another language can independently recompute a digest.
- **Recommendation.** Add pkg/nkd/canonical, owned by E0. Expose `func Bytes(v any) ([]byte, error)` producing RFC-8785 JCS-style output (UTF-8, lexicographically sorted object keys, no insignificant whitespace, canonical scalar forms) and `func Digest(domain string, v any) (string, error)` = "sha256:"+hex(sha256(domain+0x00+Bytes(v))), with a per-kind domain tag (e.g. "nkd.dev/manifest") so a vector digest can never be substituted for a manifest digest even before deserialization. Invariant baked in: the object is responsible for pre-sorting its own slices (components by name, artifacts by id) before marshaling; NO host/clock/random/UUID field may appear in Bytes() output. Every trust type implements `Marshal() ([]byte,error)` (returns canonical bytes) and `Digest() (string,error)`; add the missing attest.Manifest.Digest(). GRANDFATHER recipeDigest: ir.Graph keeps its sigs.k8s.io/yaml codec (frozen — the shipped f08265d2 depends on it) and is documented as the single exception; all NEW trust objects use canonical.Bytes. Pretty-printed JSON becomes a display-only `--pretty` view, never the hashed form.
- **Options considered.** RFC-8785 JCS compact, sorted, cross-language recomputable (recommended) · Freeze the existing json.MarshalIndent 2-space form as canonical (simplest, but harder to recompute in other languages and locks in indentation) · Reuse sigs.k8s.io/yaml everywhere (would force changing/ regrandfathering recipeDigest; YAML is a poor cross-language canonical form) · Protobuf/CBOR canonical encoding (heavier, non-human-readable, over-engineered for string-digest payloads)
- **Open questions.** (1) Compact vs indented on disk: if the file is pretty-printed but the identity is JCS-compact, publicationIdentity != sha256(file) — acceptable if defined, but must be stated explicitly (2) Is the domain-tag prefix needed given schemaVersion is already inside the bytes? (belt-and-suspenders vs redundancy) (3) Do any trust objects carry numeric fields today (all are string digests) — if not, JCS number canonicalization can be deferred
- **Artifact.** ADR-TRUST-001 (canonical serialization + digest addressing) + pkg/nkd/canonical package + golden-bytes/golden-digest test for each trust type
- **Unblocks.** E5-S6, E11-S4, E12-S1, E12-S2, E7-S2, E8-S1

#### DD-A2 — The covered-bytes vs signed-metadata vs detached-record field partition (IR-purity boundary)
`invariant · phase: sprint-0`

> **Critic note:** Merge with DD-C4 — ONE IR-purity decision (the three-tier table + the automated guard).

- **Question.** Which trust field lives in which tier — (T1) recipeDigest-covered IR bytes, (T2) signed-but-not-recipeDigest manifest/vector bytes, (T3) detached, non-covered records — so host/clock/builder/profile identity NEVER enters T1 and a detached signature never perturbs T2?
- **Why upfront.** This partition decides the shape of the IR and the manifest before code lands, and it is the recurring invariant behind E2-S4 (build record must not perturb recipeDigest), E4-S4 (reproduction tuple incl. profile), E5-S4 (signature never mutates covered bytes), E11-S4 (createdEpoch is operator-supplied, not clock), and E1-S4's import lint. If profile/host/clock leak into T1, recipeDigest becomes host-dependent and the whole zero-binary trust model collapses; every recipeDigest would churn to fix it later.
- **Recommendation.** Freeze a three-tier field-placement table. T1 (inside recipeDigest / ir.Graph, only): recipe id, resolved sources (repo+commit+treeHash+SOURCE_DATE_EPOCH), per-component toolchain digest, prebuilt content digests, the reproEnvKeys-guarded build-env allowlist, platform/arch. T2 (inside the signed manifest/vector canonical bytes, deterministic, no clock/host/random, but NOT in recipeDigest): recipeDigest itself, per-component expected sha256, profileDigest, conformanceClaim, validationVectorRef(=digest), preClassified causes, aicrRef; cosign signs these bytes and the signature is DETACHED sidecar so it never mutates them. T3 (detached, non-covered records that MAY carry host/clock): SLSA build record (builder identity, host facts, observed timestamps), ledger createdEpoch, variant expiry, status effectiveEpoch — but every 'time' is an explicit operator-supplied input parameter, never time.Now(). Add a test guard: a host/clock change alters T3 bytes while T1 (recipeDigest) and T2 (manifest bytes) stay byte-identical; extend the E1-S4 nondeterministic-import lint to cover ir+recipe+compose+attest+release+status.
- **Options considered.** Three-tier partition with time-as-input-only in T3 (recommended) · Two-tier (covered vs detached) folding profileDigest into the IR (REJECTED — makes recipeDigest host/profile-dependent) · Put builder/host provenance inside the manifest T2 (REJECTED — perturbs the signed bytes on every host and defeats define-once/publish-many)
- **Open questions.** (1) Is profileDigest strictly T2 (signed manifest) or should a copy also live in the T3 build record for audit — it can live in both as long as T1 excludes it (2) Exact allowlist of operator-supplied 'epoch/time' input fields, to keep the import lint's allowlist precise
- **Artifact.** ADR-TRUST-002 (covered-bytes vs detached-metadata partition) + a field-placement table in docs + the extended nondeterministic-import guard test
- **Unblocks.** E2-S4, E4-S4, E5-S4, E11-S4, E1-S4

#### DD-A3 — schemaVersion + additive-only migration discipline for all trust objects
`migration · phase: sprint-0`

> **Critic note:** Owns the schemaVersion registry; DD-F2 consumes it, must not declare a parallel one.

- **Question.** How is every trust object versioned, and what is the rule for adding fields later (ValidationVectorRef, aicr, preClassified, ReleaseSet binder, Inventory) so it NEVER perturbs already-published/covered bytes nor churns recipeDigest?
- **Why upfront.** The explicit E5 risk 'upgrading ValidationVectorRef string->object and adding a ReleaseSet must stay back-compatible and must not change recipeDigest or perturb covered manifest bytes' is exactly this policy. Without a stated rule, each of E5/E7/E11/E12 evolves its schema independently and someone makes a change that reshapes a signed manifest, invalidating every prior signature. The nkd.dev/<kind>/vN convention already exists (ir/attest/profile/evidence) but the evolution rule is unwritten.
- **Recommendation.** Rule set, enforced by golden-bytes tests: (1) every trust object carries schemaVersion "nkd.dev/<kind>/vN" as the canonical first field, inside the hashed bytes (a schema change => a different digest domain). (2) ADDITIVE within a major: a new field MUST be `,omitempty` and MUST serialize to nothing when unset, so an object that does not set it is byte-identical to the pre-field version — this is precisely what lets a manifest gain validationVectorRef/aicr/preClassified without perturbing manifests that don't use them (already the de-facto pattern in attest.Manifest — codify it as law). ### Domain B — Signing & Verification Architecture

This domain converts nkdctl's plumbing-only cosign path (args are built and shelled but cosign is never executed or tested — pkg/nkd/sign.SignBlobArgs/VerifyBlobArgs, cmd wiring at commands.go:754-828) into a real, executed, fail-closed trust boundary shared by attestation (E5), the verification engine (E6), and air-gapped operation (E9). The load-bearing upfront work is not implementation but four cross-epic contracts that are expensive to change once code lands: (1) a Signer/Verifier interface SEAM that six epics consume (§4.1 names E5-S1 the owner), (2) the trust-store schema + precedence rule that closes a catalog-advisory fail-open hole, (3) the trust-boundary exit-code taxonomy (today every signature/digest failure collapses to CodeVerifyFailed=22, but the stories demand a distinct code per failure class for the CI gate), and (4) the offline mirrorable-bundle format (NKD-OI-004 is explicitly TBD). Two further schema decisions — verifier isolation topology and the ValidationVector/ReleaseSet digest-addressable objects with the SEC-02 authentication chain — are hard-to-reverse and cross-owned with E12. Because cosign keyless needs a live OIDC/Rekor identity hostile to hermetic CI, every decision is designed around a local-key roundtrip for fast CI plus an OIDC/Rekor-gated integration lane.

**Package topology.** pkg/nkd/sign: add Signer/Verifier interfaces + ExecCosign real impl + FakeSigner/FakeVerifier (new seam.go), keeping the existing *Args builders as the arg layer; add SignResult/VerifyResult (carry the verified cert identity/issuer for the trust check). NEW pkg/nkd/trust: Store, Entry, Load/Save (canonical sorted YAML), ResolveExpectedSigner precedence. pkg/nkd/errors: add CodeSignatureInvalid(19), CodeUntrustedSigner(23), CodeTrustPolicyMissing(24) to the exitCodes map. pkg/nkd/attest: upgrade ValidationVectorRef string→{ref,digest} object (back-compat custom Unmarshal); add ReleaseSet + ManifestDigest (canonical-bytes sha256); wire the Signer seam into cmdAttest/cmdVerify (replace direct sign.Run calls). NEW measure-only verify path: either a pkg/nkd/verify package or a `verify --artifacts` seam that depends only on attest + a filesystem hasher and NOT on pkg/nkd/pipeline (guarded by a go-list architecture test); optionally a `verifieronly` build tag producing an isolated verifier. Test fixtures: a checked-in offline bundle + mirrored trusted-root snapshot under testdata/.

#### DD-B5 — Verifier-isolation approach — measure-only path in one binary vs a separate verifier binary/build-tag (SEC-07)

### Domain C — Reproducibility & Builder-Profile Model

This domain defines what the word "Reproduced" MEANS in nkdctl and where the line sits between the deterministic recipe identity and the host-dependent build evidence. The central design act is settling the reproduction-identity tuple (recipe x engine x input-manifest x profile) so that it captures build-SEMANTIC identity — and deliberately NOT incidental CI-adapter/runner/tool-version metadata — because one-IR-many-adapters requires github/gitlab/tekton/argo/local builds to remain mutually Reproduced, yet a genuinely different execution substrate or profile must flip to variant. Around that anchor sit four supporting contracts: a detached signing + digest-identity model for the builder profile (the currently-unproven "signed profile"); the evidence-gated hard-fail/advisory field classification plus a recipe-declared supported-profile set; an explicit IR-purity invariant with an automated guard so host/clock/engine/profile identity never leaks into recipeDigest; and the split-emit/compare two-machine bake-off protocol with a mandatory reproducibility spike. All of these are wire-schema and identity-model decisions that are expensive to reverse once E4/E5/E6/E12 encode them, so they must be locked as E0 shared trust contracts before Phase-2 code lands.

**Package topology.** - pkg/nkd/attest (attest.go, evidence.go): Manifest gains EngineClass + InputManifestDigest + ReproEnvDigest fields; VerifyAgainst extends the tuple check; new ReproTuple type (or hoisted into an E0 contracts package). Manifest/EvidenceBundle stay clock/host-free.
- pkg/nkd/profile: new profile/sign.go (detached sign/verify via the E5 Signer/Verifier seam, canonical Marshal() payload); new profile/supported.go (recipe/registry-declared SupportedSet resolution, >=1 operator-controlled enforcement); Field gains DemonstratedBy evidence ref; closed field-taxonomy constants extended (libc.class, toolchain.digest-set candidates).
- pkg/nkd/provenance (NEW) or attest/buildrecord.go: SLSA-style detached build record with a deterministic `inputs` section and a non-deterministic `observations` section (--provenance-out); consumed by E6 verify cross-check and extended by E8.
- pkg/nkd/assemble (new assemble/envelope.go): qemu-img decode-verify seam (envelope -> RAW logical stream), DiskManifestRef pre-encryption boundary marker + encrypted-envelope fail-closed.
- pkg/nkd/errors: reserve new codes in the stable exit-code contract now — CodeUntrustedProfile (19), CodeEnvelopeDecode, CodeEncryptedEnvelope — since codes never change meaning.
- pkg/nkd/recipe/compile.go + pkg/nkd/ir: UNCHANGED for purity (reproEnvKeys guard preserved); an AST/differential guard test is added over ir/recipe/compose/catalog.
- cmd/nkdctl/commands.go: preflightGate reordered strictly before resolveRecipe/source resolution; bake-off split into `emit`/`compare` subcommands with per-run scoped env (no global os.Setenv); --provenance-out and profile --require-signature paths wired.

### Domain D — Canonical Disk & Delivery Model

This domain hangs entirely off one invariant: RAW is the only canonical disk artifact and byte-identity attaches to the decoded logical LBA stream, pre-encryption only. The upfront work is (1) freezing the shared, published disk-manifest wire schema (canonical logical digest + block-range AND file-path granularity + envelopes-as-provenance + boundary/role fields), (2) a single mockable, fail-closed qemu-img decode/convert seam whose decoded-stream determinism must be spiked and whose tool version must be pinned, and (3) two hard-to-reverse policy/identity calls — the pre-encryption boundary + a new coded exit code, and role-as-SKU-identity. The one genuine technical risk gating a green FR-14 gate is the ext4 full-rootfs residual, which needs a spike to decide eliminate-vs-bound because a bound would reshape the schema and weaken the claim.

**Package topology.** pkg/nkd/assemble is the center of gravity and gains: manifest.go (canonical DiskArtifactManifest/EnvelopeRef/ContentManifest/Region + StagingManifest — the schema attest.DiskManifestRef currently stubs), codec.go (the DiskCodec seam + qemuImgCodec shelling pinned qemu-img, plus fakeCodec), iso.go (xorriso/mksquashfs-shelled ISO as a second canonical class), provision.go (ProvisioningBundle for PXE/iPXE/HTTP), fde.go (off-by-default LUKS overlay). disk.go's LogicalDiskDigest/BlockManifestOf stay but get wired into the CLI. pkg/nkd/errors gains CodeEncryptedArtifact (exit 24). pkg/nkd/attest/evidence.go's DiskManifestRef is re-expressed against the new assemble type and folded into the signed manifest. cmd/nkdctl/commands.go cmdDisk grows --format {raw,qcow2,vmdk,vhd,iso}, --role, --provision, --fde, writes a deterministic sidecar, returns coded errors. scripts/_assemble-disk.sh is demoted from the trust path to a Go-orchestrated subprocess helper (mke2fs/sgdisk/mtools/grub/xorriso stay subprocess-only for Apache-clean).

#### DD-D7 — ISO-as-second-canonical-class policy + PXE/iPXE/HTTP provisioning bundle schema
`schema · phase: phase-2`

- **Question.** Is ISO a DERIVED ENVELOPE of RAW (decode-verified back to the RAW logical digest) or its OWN canonical artifact class — and what is the deterministic PXE/iPXE/HTTP provisioning-bundle manifest (kernel+initrd+boot-script+digest list, operator-supplied base URL) that nkdctl PRODUCES but does not serve?
- **Why upfront.** E13-S3 (ISO) and E13-S5 (provisioning) both need these shapes, and the ISO classification directly affects DD-D1: if ISO is a derived envelope it needs an EnvelopeRef decode-back loop; if it is its own canonical class it does not. Getting this wrong forces a schema change after E13 code lands. The provisioning bundle is a published, digest-referenced artifact-shape consumed by downstream fleet tooling (UC-08), so its schema is a cross-boundary contract.
- **Recommendation.** Treat ISO as a SECOND canonical class, NOT a derived envelope. An ISO9660 image IS already a flat, self-describing logical byte stream (squashfs payload inside is content-addressed); qemu-img cannot decode it to a different logical stream. So a DD-D1 manifest with FormatClass=iso has LogicalDigest = sha256 of the xorriso-produced ISO bytes, NO Envelopes decode-back, determinism from xorriso + frozen faketime + sorted directory order + fixed volume-id (GPL tools shelled only). Provisioning bundle: type ProvisioningBundle struct { SchemaVersion "nkd.dev/provisioning/v1"; Kind pxe|ipxe|http; Role string; Artifacts []ProvisionArtifact (sorted by Name); BootScript string }; ProvisionArtifact struct { Name, Path, SHA256, Kind string /* kernel|initrd|rootfs|script */ }. Hard rules: BaseURL is an EMIT-TIME operator flag, never baked into any artifact; BootScript references artifacts strictly by sha256, not by mutable name; kernel+initrd derive from the canonical RAW/rootfs; nkdctl emits the bundle + digest manifest and STOPS — it never runs DHCP/TFTP/HTTP (that fleet-lifecycle boundary stays downstream, E12/NKE).
- **Options considered.** ISO as a derived envelope decode-verified to RAW (rejected: an ISO is not a block image of the RAW; there is no meaningful decode-to-RAW, so the envelope loop yields false negatives) · Bake a fixed provisioning server URL into the boot script (rejected: couples the substrate to one environment; violates 'standard interfaces, operator-provided infra') · Have nkdctl run the boot/DHCP server for convenience (rejected: crosses the produce-vs-operate boundary the whole design keeps separate)
- **Open questions.** (1) Does the ISO carry the full rootfs (live/installer) or chain to the .deb/OCI packages-first flow (thin ISO)? (2) Is iPXE script the boot artifact, or do we also emit a GRUB netboot config for pure-PXE environments? (3) Should the provisioning bundle be a variant of DD-D1 or a sibling schema referenced from the evidence bundle?
- **Artifact.** ADR 'ISO canonical + provisioning bundle' + ProvisioningBundle/ProvisionArtifact types in pkg/nkd/assemble/provision.go + iso builder spec pkg/nkd/assemble/iso.go
- **Unblocks.** E13-S3, E13-S5

#### DD-E1 — Ratify the normative layered-composition merge algebra (child-wins, scalar/slice-replace vs map-merge, enabled:false, mixin no-compose)
`invariant · phase: sprint-0`

- **Question.** What are the exact, normative merge and conflict-resolution rules FR-02 requires, and do we ratify the current pkg/nkd/compose behavior (which fixes the published recipeDigest f08265d2…) or intentionally change it?
- **Why upfront.** The rules live only in code comments + CLAUDE.md; FR-02 demands a documented spec and E1-S2 locks the flattened output with golden recipeDigest fixtures. recipeDigest is the release identity (E11 publication identity, E12 selection derive from it), so any merge-semantics change silently re-identities every published recipe — hard-to-reverse. Blocks E1-S2/E1-S3 and every downstream that treats recipeDigest as stable.
- **Recommendation.** Write docs/composition.md ratifying the current algebra as normative: (1) SELECTION — all criteria-matching overlays are composed (merge-many, not pick-one); drop any overlay that is an ancestor of another match (maximal leaves); apply order = least-specific-first, then name, base seeded first, each overlay applied exactly once (processed set). (2) CHAIN — for each leaf resolve spec.base root→leaf, child-wins. (3) COMPONENTREF merge by name: Enabled child-wins (a set value overrides); Overrides deep-merged. (4) deepMergeMap: scalar REPLACES, slice REPLACES wholesale (NO concat/union), map merges key-wise, child (src) wins per leaf, values deep-copied (no aliasing). (5) enabled:false DISABLES — the ref stays in the composed inventory for provenance but is suppressed from the effective set; a more-specific child may re-enable. (6) MIXINS: componentRefs merge by name like overlays, but constraints DO NOT compose — a name collision across the chain or across mixins fails closed (CodeInvalidCatalog). (7) DETERMINISM: every output sorted by name, AppliedLayers in deterministic order, no map-iteration leakage; override re-validation (ComposeComponents→validateComponent) runs post-merge so an override can never unpin a source or downgrade a toolchain. Cross-reference each rule to the compose.go function that implements it.
- **Options considered.** Ratify current AICR-ported behavior as normative (recommended — preserves published digests) · Change slice semantics to append/union (rejected — breaks reproducibility intuition + churns every digest) · Switch to pick-one-most-specific-recipe like the flat path (rejected — abandons the merge-many composition model the layered default relies on)
- **Open questions.** (1) Should enabled:false components appear in the SBOM/evidence inventory as disabled, or be fully elided? (2) Is a slice-of-maps at an Overrides leaf ever expected to merge-by-key rather than replace (out of scope for v1; document as replace)?
- **Artifact.** docs/composition.md (normative spec section, cross-referenced to compose.go) + docs/checklist.md §4 evidence rows
- **Unblocks.** E1-S2, E1-S3, E1-S1, E11-S4, E12-S1

#### DD-E2 — The NEW sibling-ambiguity fail-closed conflict predicate
`invariant · phase: sprint-0`

> **Critic note:** PULLED TO SPRINT-0 with DD-E1: E1-S1 (on the critical E0→E1→E2 path) implements this predicate; it must be normative before E1 code.

- **Question.** Precisely what constitutes a 'conflict' between two equally-specific, non-ancestor maximal-leaf overlays such that composition must fail closed (CodeAmbiguous) instead of silently last-wins-merging by name order?
- **Why upfront.** Today findMatchingOverlays keeps all maximal leaves and Compose merges equal-specificity siblings by name (compose_test.go:101), so two genuinely conflicting overlays resolve silently — a fail-closed hole vs. the flat CodeAmbiguous path. The predicate is genuinely new code (E1-S1) and MUST be fixed before golden fixtures (E1-S2) are cut, because it determines which sibling combinations are even legal. Over-strict detection rejects legitimate orthogonal overlays (role vs os) that examples/layered-catalog depends on — hard to loosen once operators author against it.
- **Recommendation.** Add compose.detectSiblingConflicts([]*RecipeMetadata) error, called in Compose after findMatchingOverlays, over the maximal leaves grouped by EQUAL Specificity(). For each leaf compute its WRITE SET: the union of ComponentRefs across its resolved base-chain EXCLUDING base and EXCLUDING any overlay whose name also appears in the compared sibling's chain (shared ancestors are common, never a conflict). Flatten each ComponentRef into leaves: the pseudo-path "enabled" (when Enabled!=nil) plus every dotted Overrides leaf path (recurse maps to scalars/bools/slices; a slice value is a leaf under replace semantics). A CONFLICT exists iff two siblings write the same (component,path) with values that are NOT reflect.DeepEqual. Disjoint components, disjoint paths, or identical values compose cleanly (preserves the orthogonal-leaf test). On conflict return e.New(CodeAmbiguous, ...) naming the two sorted leaf names + component + field path; recipe.resolveLayered surfaces it with the same exit code (11) the flat path yields. Sketch: type write struct{ component, path string; value any; leaf string }.
- **Options considered.** Per-(component,leaf-path) collision with deep-equal tolerance (recommended — matches E1-S1 acceptance, keeps orthogonal overlays legal) · Any two siblings touching the same component name = conflict (rejected — too strict; breaks role+os orthogonal overlays) · Whole-ComponentRef equality (rejected — misses sub-field conflicts, over-flags benign disjoint overrides)
- **Open questions.** (1) When a shared ancestor sets a value and one sibling overrides it while another leaves it, is that a conflict? (Recommend: no — one writer only.) (2) Do we also flag Enabled-vs-Overrides interplay (one sibling disables, another overrides the same component)? Recommend treating disable+override on the same component as a conflict.
- **Artifact.** docs/composition.md (conflict-predicate section) + compose.detectSiblingConflicts implementation sketch in the ADR/spec
- **Unblocks.** E1-S1, E1-S2

#### DD-E5 — Standard-interface scheme allowlist (per-field-role, permissive for operator equivalents)

#### DD-G3 — context.Context threading + subprocess cleanup-on-cancel protocol (no orphaned containers / stale output)
`invariant · phase: sprint-0`

> **Critic note:** ELEVATED to sprint-0: ctx-first + subprocess-cleanup must be baked into every Client/Runner signature from the first line. Includes a cancel-cleanup spike.

- **Question.** How does a context deadline/Ctrl-C propagate through the SDK and DAG scheduler to abort in-flight docker/git subprocesses AND guarantee no orphaned containers and no partial/stale writable output dir remain?
- **Why upfront.** ctx-as-first-param must be baked into every Client and Runner.Run signature from the start (retrofitting is a signature break across E2/E6/etc.). The cleanup semantics are a genuine technical risk called out in E14 risks: exec.CommandContext kills the docker CLIENT, not the container, and build() writes to per-node WriteDir/privOut dirs that a mid-run cancel leaves half-written and poisoning the next run. Must be proven by a spike before the scheduler is committed.
- **Recommendation.** Thread ctx: add ctx as first arg to every Client method and to Runner.Run(ctx,g,digest,opts); convert every exec.Command in pipeline/local.go, pipeline/pull.go, pipeline/vendor, catalog/pin.go, sign/sign.go to exec.CommandContext, and set Cmd.WaitDelay + Cmd.Cancel (SIGTERM then SIGKILL grace) so a killed process is reaped. Scheduler checks ctx.Err() before dispatching each node and between ticks, returns errors.New(CodeTimeout,...) on deadline/cancel. main.go: signal.NotifyContext(SIGINT/SIGTERM) root ctx + global --timeout wrapping it via context.WithTimeout. - **Open questions.** (1) Grace period before SIGKILL for an in-flight go build (WaitDelay value)? (2) Do we also need a `nkdctl gc`/orphan-sweep for containers leaked by SIGKILL of nkdctl itself (kill -9), which no defer can catch? (3) Should --timeout default to unset (0) or a large safety default?
- **Artifact.** Spike report docs/spikes/cancel-cleanup.md + a cancellation test (scripts/cancel-spike.sh) + ADR section on the container-naming/cleanup registry

- **Recommendation.** Inject a log/slog.Logger via WithLogger (default: slog text handler, level=warn, to stderr). Migrate all diagnostic fmt.Fprintf(os.Stderr,...) to it. INVARIANT: result streams (recipe IR, SBOM, expected-digests manifest, pipeline.Report, evidence bundle) go to stdout or --out files ONLY; stdout carries zero log lines. Global `--log-level {error,warn,info,debug}` + `NKDCTL_LOG` env (flag wins); honor NO_COLOR (and non-TTY) to disable any ANSI. Report-producing commands accept `--output {text,json}` (default text/human): with json, stdout is a SINGLE valid document — either the raw canonical artifact (IR YAML/JSON, CycloneDX JSON) or, for multi-field results, one stable top-level JSON object `{schemaVersion, ...}` (sorted keys, deterministic). Guard with a test that captures stdout+stderr for `resolve --output json`: stdout parses as one document with zero log lines, all logs on stderr, NO_COLOR yields no escape bytes.
- **Options considered.** Log to stdout with a --quiet flag — rejected: contaminates the result stream and breaks piping · zerolog/zap dependency — rejected: stdlib log/slog is Apache-clean and sufficient; avoid a new linked dep · Per-command ad-hoc json — rejected: no stable envelope for consumers; must be one documented shape with schemaVersion
- **Open questions.** (1) Does the json envelope need a top-level schemaVersion per result type now (recommended, ties into E8 schemaProfile) or later? (2) Should progress/step logs default to warn (quiet) or info? (recommend warn so stdout+default stderr stays terse for CI)
- **Artifact.** Spec docs/output-contract.md (stdout/stderr rules, log levels, NO_COLOR, --output json envelope) + a stdout/stderr separation test
- **Unblocks.** E14-S9, E0, E8-S2

#### DD-G5 — Bounded query/diff selector grammar + diff exit-code convention (not a JSONPath engine)
`schema · phase: phase-3`

- **Question.** What is the minimal, deterministic selector grammar for `query`, how does `diff` compute the minimal reproducible recipe diff, and what exit code signals 'differs' without colliding with the error map?
- **Why upfront.** E14 risk: selector semantics drift toward a full JSONPath engine, which is non-deterministic-surface and a heavier dep. The diff OUTPUT is a handoff contract consumed by the CVE fast-path (E11/E12, INT-039/040), so its format and 'has-changes' signaling must be pinned before those consumers parse it. Hard to reverse once external tooling depends on the grammar and the diff exit convention.
- **Recommendation.** Define a CLOSED grammar over the deterministic IR canonicalized to JSON: a path is `.` -separated segments; each segment is a field name (matching IR json tags) or a list accessor `[*]` (all), `[<int>]`, or `[<key>=<value>]` (filter objects). Validate the whole selector against a single regex before evaluation (no recursion, no expressions, no functions). e.g. `.recipeDigest`, `.components[*].toolchain`, `.components[name=kubelet].commit`. Output: scalar -> print value; list -> newline-delimited (or a json array under --output json). A malformed selector -> CodeUsage(2); a syntactically-valid but absent path -> CodeNoMatch (deterministic, fail closed). diff: operate over two IRs' canonical JSON, emit the SORTED minimal set of changed PINNED leaf paths (commit/treeHash/toolchain digest/artifact digest) as `path: from -> to`; a single-commit bump yields one line. Because exit 1 = internal error, diff must NOT use 1 for 'differs': the command sets a dedicated non-error exit 40 ('differences present') explicitly, bypassing ExitCode (0 = identical, 40 = differs, error codes only on failure). Document 40 in the exit-code table as a semantic (non-error) status.
- **Options considered.** Adopt full JSONPath (e.g. a library) — rejected: heavier dep, non-deterministic surface, scope creep the Epic explicitly warns against · Reuse `recipe -o digest/components` only — rejected: cannot extract an arbitrary pinned field (INT-016 unmet) · diff exits 1 on differences (diff(1) convention) — rejected: 1 is our internal-error code; a distinct 40 keeps 'differs' separable from 'failed' · Emit diff as a JSON patch (RFC-6902) — rejected: over-general; the minimal-pinned-leaf list is the handoff contract consumers actually need
- **Open questions.** (1) Is exit 40-for-differs acceptable to the CVE-fast-path consumer, or do they prefer 0+parse-the-body? (align with the Domain owning E11/E12) (2) Does query need list output as json-array-only or also newline text by default? (recommend newline text, json under --output json)
- **Artifact.** Spec docs/selectors.md (EBNF grammar + examples + the diff minimal-pinned-leaf format + exit-40 convention)
- **Unblocks.** E14-S5, E11-S5, E12, E14-S6

#### DD-H1 — PinnedInput immutable-identity model + content-addressed mirror layout
`schema · phase: phase-0`

> **Critic note:** PinnedInput is THE single pinned-input identity type; the DD-A5 Inventory references it, not a parallel schema.

- **Question.** What is the canonical immutable-identity string for every pinned input (git source, per-arch toolchain, prebuilt artifact, package snapshot, base image), and what on-disk content-addressed store layout do `nkdctl inputs`, `nkdctl mirror`, and `bundle --airgap` all read/write?
- **Why upfront.** E9-S3/S4/S5 serialize/consume this, and the SAME 'immutable identity' notion is reused by E9-S6 (toolchain), E11-S3 (verify-pins retrievability audit) and E12-S4 (registry-by-digest select). The identity string is embedded in the airgap bundle's top manifest and referenced by external mirrors; the on-disk store layout is hard to reverse once operators publish mirrors. Deciding it late forces re-mirroring and bundle-format churn across all four CI adapters.
- **Recommendation.** One PinnedInput type: {Kind: git|toolchain|artifact|package-snapshot|base-image; ID; Arch ("" for arch-agnostic git); Identity (self-verifying locator); Digest sha256:<hex> = content address; Locator (upstream URL/ref, PROVENANCE ONLY, never trusted in airgap)}. Canonical byte-stable Identity forms: git = `git:<repo>@<commit>@<treeHash>`; toolchain/base-image = `oci:<registry>/<repo>@sha256:<hex>`; artifact = `https:<sha256>` (content, not URL) or `oci:...@sha256`; package-snapshot = `snapshot:<mirror-host>@<yyyymmddThhmmssZ>#<subsetDigest>`. `nkdctl inputs` emits sorted([]PinnedInput) as canonical JSON (no host/clock/random), one manifest per platform. Store layout under <dir>/: `inputs.json` (self-describing top manifest) + `blobs/sha256/<hex>` (every stored blob, addressed by content digest) + `by-identity/<escaped-Identity>` index into blobs. `nkdctl mirror` fetches each input once, verifies bytes==Digest, fails closed (CodeUnpinnedInput on a non-content-addressable input, CodeMirrorMismatch on hash drift). `bundle --airgap` rewrites the IR's repo/toolchain/artifact fields to `by-identity/...` refs and ships inputs.json as the self-describing top manifest so all four emitters lower a relocated IR carrying no upstream URL for any pinned input.
- **Options considered.** (a) content-addressed blob store keyed by sha256 with an identity index (RECOMMENDED — dedupes, matches OCI/skopeo, no host paths in bytes) · (b) per-kind directories keyed by logical name (simpler, but no dedup and leaks host-path-shaped keys) · (c) reuse an OCI registry as the store (heavier; requires a registry running inside the airgap)
- **Open questions.** (1) package-snapshot subset scope — size and licensing of a mirrored apt/deb subset (2) git stored as a `git bundle` vs a tree tarball (tarball is easier to hash byte-stably; ties to DD-H2) (3) escaping scheme for `by-identity/` filenames so the index is portable across filesystems
- **Artifact.** Schema doc docs/schemas/pinned-input.md + a golden inputs.json fixture per arch for the embedded default catalog (determinism/regression baseline).
- **Unblocks.** E9-S3, E9-S4, E9-S5, E9-S6, E11-S3, E12-S4

#### DD-H2 — IR relocation & vendored-tree reproducibility (zero-egress build spike)
`spike · phase: phase-1 (run early)`

> **Critic note:** Run early alongside DD-C6 — a non-byte-identical vendored tree breaks the airgap IR-relocation design and touches recipeDigest.

- **Question.** Can the non-vendored sources (etcd/coredns/helm) have their module deps pre-materialized into a BYTE-IDENTICAL vendored source tree so an airgap `--network=none` build yields the SAME recipeDigest and component digests as the online vendor-at-build run — and does vendoring happen at PIN time (baked into the source pin's treeHash) or at mirror time?
- **Why upfront.** E9-S4/S5 depend on this and it is a genuine technical risk: if `go mod vendor` output is not byte-stable across differing proxy/GOFLAGS/cache state, the 'relocate the IR to a mirror' design breaks (the hermetic digest drifts). The fix (vendor at pin time so treeHash covers vendor/) changes the source-pin schema AND recipeDigest itself — a hard-to-reverse change that also touches E11's pin machinery. Must be proven before committing E9's approach.
- **Recommendation.** Run scripts/airgap-vendor-spike.sh: for each non-vendored source, `go mod vendor` under two deliberately-different environments (differing GOPROXY, GOFLAGS, module cache, TZ, HOME) with GOTOOLCHAIN=local + GOFLAGS pinned, hash the resulting vendor/ tree, assert byte-identity (this mirrors the existing Phase-1 bake-off discipline). If it HOLDS, adopt PIN-TIME vendoring: `catalog pin` runs `go mod vendor` and folds the vendored tree into the source's treeHash, so the vendored bytes become part of recipeDigest and the IR has NO vendor step at all — every source is pre-vendored and every build is `--network=none`. If it does NOT hold, fall back to storing the vendored tree as a distinct content-addressed PinnedInput (Identity `git:<repo>@<commit>@<vendoredTreeHash>`) and pin the vendoring env in the IR reproEnvKeys guard. Reject keeping the `--network=default` vendor step — it fails FR-19 for these three components.
- **Options considered.** (a) vendor at PIN time, treeHash covers vendor/ (RECOMMENDED — makes the digest honest and airgap trivial; one treeHash to verify) · (b) vendor at MIRROR time into a separate content-addressed tree (lighter pin, but adds a second treeHash to verify and a re-materialization step) · (c) keep the online vendor step and accept airgap cannot build etcd/coredns/helm (REJECT — violates FR-19)
- **Open questions.** (1) does `go mod vendor` output vary across Go patch releases (mitigated by the existing GOTOOLCHAIN=local pin)? (2) do any of the three sources run build-time codegen that itself needs network? (3) on-disk size of the three vendored trees added to the mirror
- **Artifact.** Spike report docs/spikes/airgap-vendor-reproducibility.md with the two-environment hashes and the pin-time-vs-mirror-time decision.
- **Unblocks.** E9-S4, E9-S5, E9-S7

#### DD-H3 — Toolchain mirrorability policy — local image ID -> registry digest (fail-closed vs push)
`policy · phase: phase-0 · ⚑ product/org`

- **Question.** The kubernetes/runc toolchains are pinned as LOCAL image IDs (toolchainImagesByArch) that cannot be mirrored by immutable identity. Under airgap, do we fail closed until an operator pushes them to a registry and re-pins the registry digest, or does nkdctl push+pin? And what lock-schema slot records the mirrorable digest?
- **Why upfront.** E9-S6 is blocked and E9-S3 `inputs` must decide whether a local-ID toolchain is a fail-closed input or a mirrorable one. Adding a mirrorable-digest field to the lock is a hard-to-reverse schema change, and the whole thing hinges on an operator REGISTRY to push to — a real org/infra dependency, not a pure code decision (called out explicitly in the E9 risks).
- **Recommendation.** Policy = FAIL-CLOSED-UNTIL-MIRRORED by default, with an opt-in push. Add a per-source lock field `toolchainMirror: {amd64: registry/repo@sha256:..., arm64: ...}`, populated by a new `catalog pin-toolchains [--push <registry>]`: it docker-tag/push the locally-built image, reads back the registry digest, records it (machine-managed, deterministic). `nkdctl inputs --airgap` treats a source lacking a toolchainMirror entry as a fail-closed input (CodeUnpinnedInput, naming the source) unless `--allow-local` is explicitly passed (a non-airgap escape). The IR validator already accepts any per-arch digest form; an airgap build resolves the toolchain from the mirror BY its registry digest (skopeo/docker load), never rebuilding it locally. Reject nkdctl always-pushing (couples pin to infra, breaks offline `make test`) and reject rebuilding the toolchain in-airgap (defeats the digest pin; the base still needs mirroring).
- **Options considered.** (a) fail-closed-until-mirrored + opt-in `catalog pin-toolchains --push` (RECOMMENDED — keeps default trust honest, no forced registry dependency) · (b) nkdctl always pushes to a caller registry on pin (couples pin to infra; breaks offline test) · (c) rebuild the toolchain in the airgap from a mirrored Dockerfile+base (REJECT — abandons the digest-pin discipline)
- **Open questions.** (1) which registry does the org own for this, with immutability/retention for the release lifetime? (2) does pushing yield a stable manifest digest vs the local single-arch image ID (manifest-list vs per-arch)? (3) who runs pin-toolchains — publisher CI, or each operator locally?
- **Artifact.** ADR docs/adr/0007-toolchain-mirrorability.md + the `toolchainMirror` lock-schema addition and a test over the default catalog asserting all 8 sources resolve to registry digests or the documented fail-closed case.
- **Unblocks.** E9-S3, E9-S6, E9-S7

#### DD-H5 — Runtime-conformance handoff contract (ConformanceResult object, binding, signer trust)
`schema · phase: phase-0 · ⚑ product/org`

- **Question.** What is the wire shape of the externally-produced runtime-conformance result nkdctl ingests, how is it cryptographically bound to the release member (recipeDigest + vectorDigest), and what is its signer/trust model so a forged or stale result cannot satisfy the SEC-08 second gate?
- **Why upfront.** E12-S3 is blocked, and the binding fields constrain DD-H4's ValidationVector identity (the result must reference the vector Digest). This is a contract with an EXTERNAL producer (the conformance suite / NKE — non-normative and under-specified in the SRD), so the wire schema is hard to reverse and a weak binding is a security hole (the E12 risk log flags exactly this). It needs an upfront, human/org-owned decision on the signer trust boundary.
- **Recommendation.** release.ConformanceResult{SchemaVersion; BoundRecipeDigest (MUST==member recipeDigest); BoundVectorDigest (MUST==member ValidationVector.Digest()); Suite; SuiteVersion; Verdict passed|failed; ResultsDigest (sha256 of the raw suite output, OPAQUE to nkdctl); EffectiveEpoch (operator-supplied INPUT, never time.Now)}, deterministic + digest-addressable, consumed as an INPUT only (nkdctl NEVER runs the cluster). release.Gate rule: a member is promotable only if reproduction ∈ {reproduced, validated-variant} AND a ConformanceResult with Verdict==passed exists AND its BoundRecipeDigest/BoundVectorDigest match the member; a missing result => conformance=absent => CodeGateUnmet (NEVER inferred from the reproduction verdict). The result MUST be independently signed (same cosign seam) by a conformance-signer identity DISTINCT from the build/publish identity (`--conformance-identity`/`--conformance-issuer`); under `--require-conformance-signature` (default ON for `release promote`) an unsigned or wrong-identity result is rejected. This IS SEC-08 verifier isolation in wire form. Reject unsigned file-location trust (forgeable) and reject nkdctl running the suite (breaks verifier isolation + the E12 boundary discipline).
- **Options considered.** (a) signed, independently-identified result bound by recipeDigest+vectorDigest (RECOMMENDED) · (b) unsigned result trusted by file path/location (REJECT — forgeable/stale) · (c) nkdctl runs the conformance suite itself (REJECT — breaks verifier isolation and the produce-not-operate boundary)
- **Open questions.** (1) who owns the conformance-signer identity — NKE, or a separate org role? (2) is the raw suite output a standardized format (e.g. sonobuoy tarball) — nkdctl treats it as opaque ResultsDigest, but the producer contract must be agreed (3) expiry/staleness semantics of a passing result (does EffectiveEpoch age out a pass?)
- **Artifact.** ADR docs/adr/0008-conformance-handoff.md + JSON Schema docs/schemas/release/conformance-result.json.
- **Unblocks.** E12-S3, E12-S5

#### DD-H6 — Digest-first selection + rollback-as-reselection invariant
`invariant · phase: phase-0`

- **Question.** What resolution rule guarantees a mutable registry tag can never bypass digest+signature verification (SEC-13), and what does rollback restore — an infra action, or a re-verified re-selection by immutable digest only (UC-15)?
- **Why upfront.** E12-S4/S6 are blocked. 'Effective selection is ALWAYS the resolved digest, never the tag' is a pervasive, hard-to-reverse invariant that EVERY ref-handling path (release verify/promote/rollback, E9 mirror resolution, E11 immutable identity) must obey from the first line of code; retrofitting tag-trust out later is dangerous. It also enforces the E12 boundary discipline: nkdctl re-selects, it does not mutate the fleet.
- **Recommendation.** Single choke-point release.Resolve(ref) (Resolved, error): name@sha256:<hex> used directly; name:tag resolved to its CURRENT digest, and the RESOLVED DIGEST becomes the effective selection recorded everywhere (the tag string is never persisted as identity); after resolution, digest+signature verified via sign.VerifyBlobArgs with pinned identity/issuer, failure => CodeUnverifiedRef; if the caller supplied an expected digest and the served digest differs => fail closed naming served-vs-expected; offline path uses the DD-H1 mirror + the mirrored-bundle Rekor inclusion proof, no network. Rollback = PURE reselection: `release rollback --to <releaseSetDigest>` REQUIRES an immutable set digest (a tag/mutable ref => CodeUnverifiedRef), re-runs the full E12-S5 clearance path against the target, and only on full pass emits a deterministic release.Selection{ActiveReleaseSetDigest, Supersedes}; nkdctl performs NO infra mutation; re-running rollback to the same digest is byte-idempotent. Assert by test that no code path persists or trusts a tag string as identity. Reject resolve-at-each-callsite (invariant leaks) and reject rollback triggering an infra action (violates the boundary).
- **Options considered.** (a) central Resolve choke-point returning a verified digest; rollback re-selects only (RECOMMENDED) · (b) resolve-and-verify at each callsite (REJECT — invariant leaks, easy to forget the verify step) · (c) rollback performs the infrastructure rollback (REJECT — violates E12 produce-not-operate discipline)
- **Open questions.** (1) what is 'current digest' for a tag under a compromised registry offline — must compare to the operator-supplied/mirrored expected digest (2) signature discovery: OCI referrers API vs a sibling .sig/.bundle (3) how the pinned signer identity/issuer are distributed to an airgapped operator
- **Artifact.** ADR docs/adr/0009-digest-first-selection.md documenting the never-trust-a-tag invariant plus the Resolve/rollback signatures and the Selection object.
- **Unblocks.** E12-S4, E12-S6, E9-S5

#### DD-H7 — Status-declaration schema + consumption trust surface (withdraw-DoS defense)
`schema · phase: phase-3 · ⚑ product/org`

> **Critic note:** Schema skeleton frozen in sprint-0 with DD-H4; consumption trust policy is phase-3.

- **Question.** What is the StatusDeclaration wire shape, and what require-status-signature enforcement semantics prevent an attacker-supplied `withdrawn` declaration from DoS-ing a good release while still honoring a legitimate withdraw (UC-11 / SEC-16)?
- **Why upfront.** E11-S6/S7 are blocked. The declaration is a new deterministic wire object (hard to reverse) and its consumption is a security-sensitive trust surface: fail-open (ignore unsigned withdraws) risks honoring a forged one, while fail-closed-on-any-withdraw lets an attacker DoS a good release — the E11 risk log flags this precisely. The DEFAULT enforcement policy is a product call that must be pinned before verify/resolve consume declarations.
- **Recommendation.** New pkg/nkd/status; StatusDeclaration{SchemaVersion; Target (immutable publication identity/digest ONLY — a non-digest target => fail closed); Action superseded|deprecated|withdrawn; ReplacedBy (required iff superseded, an immutable identity); Reason; EffectiveEpoch (operator-supplied INPUT, never time.Now)}, deterministic (sorted keys), identity = content digest, and `status declare` never opens/rewrites the target manifest/ledger/evidence. Consumption policy (verify/resolve `--status <dir>`): an UNSIGNED/unverifiable declaration is IGNORED for enforcement by default; with `--require-status-signature` a signature is mandatory and an invalid/missing one fails closed — so a bare attacker-dropped `withdrawn` file does nothing unless it carries a signature from the pinned `--status-identity`/`--status-issuer`. A SIGNED withdrawn from the pinned identity => CodeWithdrawn + nonzero exit; deprecated => warn+proceed; superseded => warn + name ReplacedBy. A future-dated EffectiveEpoch is NOT enforced (no clock imported into enforcement; inert until an operator passes an as-of epoch), preserving determinism. Anchor trust to the same keyless identity model as the release, NOT to file presence. Reject honoring any withdrawn file (trivial DoS) and reject a required online revocation check (breaks offline discipline).
- **Options considered.** (a) signed-only enforcement anchored to a pinned status-signer identity, unsigned ignored (RECOMMENDED — defeats the DoS while honoring legit withdraws) · (b) honor any withdrawn declaration by file presence (REJECT — trivial denial-of-service on a good release) · (c) require a fresh online revocation check at consume time (REJECT — breaks offline/airgap equivalence)
- **Open questions.** (1) is the status-signer identity the SAME as the publish identity or a distinct role? (2) reinstatement semantics — can a later signed declaration override an earlier withdraw (ledger order by EffectiveEpoch)? (3) how the pinned status identity is distributed to an airgapped consumer
- **Artifact.** ADR docs/adr/0010-status-declaration-trust.md + JSON Schema docs/schemas/status-declaration.json + CodeWithdrawn registration in errors.go.
- **Unblocks.** E11-S6, E11-S7
