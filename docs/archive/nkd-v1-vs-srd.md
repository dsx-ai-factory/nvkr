## Bottom line

`nkd-v1.md` specifies **NKD**, a versioned, NKE-coupled *product/catalog* (an immutable signed distribution recipe + reproducible pipeline + signed builder profiles + validation vectors + product lifecycle), while `docs/srd.md` specifies **nkdctl**, the environment-agnostic Apache-2.0 *tool* a catalog like NKD rides on. They sit on the two deliberate sides of the TOOL/CATALOG split and agree strongly on the load-bearing invariants: recipe-before-artifacts, zero-binary trust (publish signed digests, not bytes), fail-closed, thin CI adapters over one build core, and reproducibility-as-trust. The SRD faithfully realizes NKD-v1's product intent for the build/verify half and is far more mechanistic (recipeDigest, cosign/Rekor stack, catalog resolver, hermetic-container discipline); most divergences are expected product-vs-tool scope gaps. **The one substantive conflict is real and recurs in two forms:** (1) NKD-v1 declares qcow2 a *derived envelope explicitly NOT byte-reproduced*, while the SRD mandates qcow2 **SHALL** be byte-reproducible; and (2) NKD-v1 bounds byte-identity to a single *signed builder profile* (host/kernel pinned; differing host = a non-reproducing "variant"), while the SRD makes **cross-environment (differing kernel/CPU) bit-identity its definitive pass criterion**. These are the resolve-before-v1 items.

## Confirmed conflicts

The audit returned exactly **two distinct real conflicts** (the qcow2 one surfaced under four themes; the reproducibility-scope one under two). One candidate — the hedged/provisional framing at SRD lines 7, 242 — was rated **nuance-not-conflict** and is noted below.

**1. qcow2 (and VMDK/VHD) byte-reproducibility.** `real-conflict`.
- SRD `NKD-FR-BLD-063` (477) [MUST]: "Bootable disk images (qcow2, ISO, raw, tarball) SHALL be byte-reproducible for a given resolved recipe, using deterministic filesystem/image tooling (fixed GPT GUIDs, `mke2fs -U`, `mksquashfs -all-time`, pinned `xorriso`)." Reinforced by INT-020 (671, qcow2 "first-class") and REP-001 (535, byte-identical "disk images (pre-encryption)").
- NKD-v1 non-goal (148) + §8.3.1 (305–317): "This is a deliberate change from treating QCOW2 as a byte-reproduced artifact... QCOW2, VMDK, VHD | derived envelope | ... The container file itself is **not** compared" — only the decoded logical-disk digest must equal the reproduced RAW; RAW is "the only disk format whose byte boundary is unambiguous."
- **Why it matters:** A catalog built by nkdctl-per-SRD ships byte-reproduced qcow2 images that NKD-v1 declares out of scope and technically claims *cannot* be byte-stable ("vary across otherwise identical hosts," 307). NKD-v1's "deliberate change" language shows the authors consciously reversed the SRD's stance. Same-artifact, same-property, opposite requirements.

**2. Byte-identity scope: cross-environment (hermetic) vs single signed builder profile.** `real-conflict`.
- SRD `NKD-NFR-002` (769) [MUST]: "nkdctl SHALL demonstrate bit-identity of all in-contract artifacts across **two distinct build environments** (differing host OS, kernel, CPU, wall-clock). This cross-environment bit-identity is the definitive pass criterion, not same-host repeatability." `NKD-FR-BLD-070` (499): a non-identity bake-off result "SHALL fail the gate."
- NKD-v1 §10.1 (490, 502): "Byte-for-byte reproduction... within a published supported builder profile. It is not a cross-profile guarantee... A customer-supplied base image or host property that differs from the selected profile produces a variant and cannot claim byte identity."
- **Why it matters:** Take one concrete case — two different host kernels. The SRD declares byte-identity *mandatory and the definitive pass*; NKD-v1 classifies it a "variant," not a reproduction, and affirmatively lists runner kernel/virtualization as byte-affecting. A single system cannot both require and deny this. This is the deeper root of the qcow2 conflict (NKD's profile pins the host *because* it treats the host as byte-determinative; the SRD's hermetic-container thesis treats it as non-determinative).

**Nuance-not-conflict worth awareness:** The abstract-level version of conflict #2 at SRD lines 7/242 is explicitly hedged — the two-environment bake-off is "a mandatory gate before committing to the from-source thesis; this architecture is provisional," and two-machine bit-identity is recorded as "Deliberately NOT done." As an *ambition/gate* this is reconcilable with a product that bounds its customer guarantee; the collision only becomes hard at the unhedged MUSTs (499/769).

## Gaps: in the SRD (present in NKD-v1, missing/weaker in the SRD)

- **Signed builder-profile construct** — an immutable declaration of runner/kernel/arch/filesystem/container-runtime/virtualization/toolchains/locale/clock as the authoritative reproducibility identity, with a fail-closed host preflight and re-baseline SLA/grace/deprecation windows (nkd-v1 187, 249–284, 490–502). No analog; the SRD relies on hermetic pinned-by-digest containers.
- **ValidatedVariant / controlled-fallback path** — a signed, time-bounded, two-tier (pre-classified auto / novel signed) gated exception with a distinct identity that "never claims byte reproduction" (nkd-v1 165, 337–359). The SRD only fails closed.
- **Kubernetes conformance + validation vectors** — per-recipe conformance claim, the full NVIDIA release-validation suite, operator runtime conformance against the instantiated cluster, and the two-independent-vectors rule (reproduction AND runtime conformance both gate promotion) (nkd-v1 514–523, 634–691). SRD "validation" is static catalog + repro + digest verify only.
- **Runtime drift model** — node MUST report recipe/release-set identity; unrecognized mutation = drifted; EmergencyDrift/UnsupportedDrift state machine + reconciliation deadlines/support-SLA (nkd-v1 459–470, 527–532). The word "drift" never appears in the SRD.
- **Accelerated-runtime / AICR profile as a v1 goal** and NKE compatibility contract — AICR profile identity+digest, compatible-NKE versions, §8.5 NKE consumption contract, lifecycle state/support dates/upgrade sources carried in the recipe (nkd-v1 79, 132, 214, 216–226, 378–389). SRD scopes GPU/accelerated and NVIDIA-internal systems out.
- **Product/support/observability surface** — NVIDIA-vs-operator responsibility & incident-liability boundary (release blocker), digest-mismatch triage with cause-code taxonomy + signed evidence bundle, OpenTelemetry metric/log/trace + audit-trail contract, verifier independence/isolation from build stages, promotion-time malware/vuln scanning + build provenance as distinct signed evidence (nkd-v1 514/525, 561–590, 620–632, 693–767).
- **Per-format canonical-boundary taxonomy** — RAW-as-sole-canonical-OS-artifact with derived-envelope conversion after Reproduced; per-block-range + per-path + per-package Merkle-like manifests to make mismatch diagnosable without reference bytes (nkd-v1 301–319, 361–376).
- **Program apparatus** — 4-phase rollout with exit criteria (§16), product P0 + ~14 success metrics (§17), 21-row product risk table (§18), 20 numbered open decisions (§19).

## Gaps: in NKD-v1 (present in the SRD, missing/weaker in NKD-v1)

- **Explicit TOOL/CATALOG separation** — a general-purpose tool distinct from any catalog, a `DataProvider` abstraction, a `//go:embed` default catalog, and a `--data` override that *fully replaces* it; "NKD" carries no privileged status (SRD 37, 51–58, 173, 263, 379–383). NKD-v1 fuses recipe+engine+profiles+vectors into one product.
- **Declarative SourceBuildRegistry catalog** — each buildable component is a single YAML entry (add a component = no code change) pinning repo, tag→full SHA, expected tree hash, ordered content-addressed patch series, canonical build command, toolchain digest, per-entry CGO lane, and pluggable outputType (SRD 338–354). NKD-v1 stays at coarse source-digest granularity.
- **Criteria resolution front-end** — asymmetric wildcard match over active axes `role × k8sVersion × os × arch` (arch multi-arch), specificity tie-break, six reserved axes that fail closed, deterministic multi-catalog precedence reflected in recipeDigest (SRD 265–313, 376–377). NKD-v1 authors a recipe by version with no resolver.
- **`recipeDigest = sha256(deterministically-marshaled IR)`** as the single named identity anchor binding manifest/SBOM/verify, with the IR fully enumerating inputs so no stage re-reads the catalog (SRD 326–332, 538–540, 663). NKD-v1 has "recipe digest" in its tuple but does not bind SBOM/verify to it as explicitly.
- **Concrete signing/verify stack** — cosign keyless + Fulcio + Rekor inclusion proof, detached; publisher-agnostic (no hardcoded NVIDIA issuer), configurable OIDC, a `trust` command, and a **mandatory mirrorable Rekor bundle** for fully-offline verify (SRD 558–592, 711, 737). NKD-v1 leaves the scheme "open" and offline mechanism TBD.
- **Explicit build-from-source mandate + reproducibility discipline** — no-prebuilt-binary/image/chart rule; `--network=none` + env allowlist; the full Go flag set (`CGO_ENABLED=0`, `-trimpath`, `-buildvcs=false`, `-ldflags=-buildid= -s -w`, `GOTOOLCHAIN=local`); `SOURCE_DATE_EPOCH` from committer `%ct`; runc CGO/pause C lanes; Apache-2.0 build-runtime constraint; mmdebstrap base rootfs; airgap vendoring mode (SRD BLD-010..031, 417–446, 485, REP-004..006). NKD-v1 abstracts these into an opaque engine and even pins a prebuilt base-image OCI as input.
- **Byte-deterministic self-emitted artifacts** — deterministically serialized CycloneDX SBOM (stripped serialNumber/timestamps, UUIDv5) and re-serializable manifest yielding byte-identical output (SRD 596–600).
- **Packages-first / BYO-OS** as the primary mode with a thin optional image, plus a generic machine-readable handoff contract to *any* downstream lifecycle system, and the engine-neutral adapter set incl. Tekton/Argo/local (SRD §3.5, 514–522, 719, BLD-002).
- **Formal document machinery** — versioned draft, revision history, intended-audience list, MoSCoW priorities, §9 Constraints table, §10 consolidated Out-of-Scope, decided amd64-only v1 (SRD Doc Control, 865–914).
- **In-catalog Tier-4 exclusion** — a "cannot-build-from-source" component carried as a validated declared exception, never emitted as a build node, with named examples (SRD 364, 1235–1242).

## Recommendations

1. **Resolve the qcow2 conflict explicitly (highest priority).** Reconcile SRD `BLD-063`/`INT-020`/`REP-001` with NKD-v1 §8.3.1. Recommended: amend the SRD so the byte-reproducibility MUST attaches to the **RAW / decoded logical-disk stream**, and reclassify qcow2/VMDK/VHD as derived envelopes verified by logical-disk digest (adopt NKD-v1's canonical-boundary-per-format taxonomy). This aligns the tool with the product's deliberate, technically-grounded position and removes a contradiction the tool cannot actually satisfy.
2. **Resolve the reproducibility-scope conflict.** Decide whether the tool guarantees cross-environment bit-identity (SRD `NFR-002`/`BLD-070`) or bounds it to a declared host profile (NKD-v1 §10.1). Either (a) demote the SRD's cross-environment claim from a MUST to the already-hedged provisional gate and add a builder-profile concept, or (b) keep the hermetic thesis but scope the profile-independence claim to the components/toolchains actually proven bit-identical two-machine — and land the two-machine spike (CLAUDE.md lists it "Deliberately NOT done"), since the entire trust model rests on it.
3. **Add a ValidatedVariant / controlled-fallback story to the SRD (or explicitly delegate it).** The pure fail-closed model is cleaner but leaves no path for documented host/representation nondeterminism; either add a gated signed-exception lane or state that variant governance is a catalog-layer concern above the tool.
4. **Add conformance + runtime-verification requirements or a clean handoff.** The SRD equating "verified bytes" with a correct cluster is a silent gap; add either a downstream conformance-vector handoff requirement or explicit language that runtime k8s conformance is out of the tool's remit (it currently is only by omission).
5. **Import NKD-v1's diagnosability + verifier-isolation requirements.** Add a stable mismatch cause-code taxonomy, a signed evidence bundle spec, and a "verifier SHOULD be independently implemented/isolated from build stages" requirement so one defect cannot forge both artifact and proof.
6. **Fix the "Phase 1/2" terminology collision.** NKD-v1 uses Phase 0–3 for rollout; the SRD uses Phase 1/2 for the BYO-OS consumption model. Rename one to avoid cross-document confusion.
7. **Cross-reference the two docs.** Have the SRD name NKD as its canonical example catalog and cite NKD-v1's canonical-boundary/profile sections; have NKD-v1 reference the SRD as the tool contract it publishes on top of — making the intended TOOL/CATALOG layering explicit and auditable.
