# Local ARM64 provider source builds, October 7, 2026

## Scope

One real NKD local Run compiled CAPNICo and the provisioned infrastructure provider
from pinned Git, then observed their OCI payloads, generated composition SBOMs and
packaged the images. Both images loaded into rootless Podman and executed their
help entrypoints offline. This is unqualified local execution, not cluster
deployment, full NKE acceptance, upstream signature verification, publication,
signing or qualified reproduction.

The Run used implementation base `fb6ee5e71adf6baeacfb18d7be042224ec3691b1`
with the provider input/launcher additions in this change. The runner reported
`fb6ee5e-dirty`; exact exercised input and runner file hashes are retained below.
Documentation and contract-test additions after the bake did not alter its
provider instructions. A future committed-head replay is distinct evidence.

## Execution

From the managed NKE Recipes worktree on an Apple Silicon laptop:

```sh
NKE_LOCAL_CLONE=/absolute/path/to/nke \
  bash scripts/nke-full-arm64-local.sh laptop-providers-arm64-20261007-01 2 providers
```

The launcher compiled a static Linux ARM64 NKD with the repository Go patch and
entered the existing `podman-machine-default` VM as its rootless `core` user.
`NKE_LOCAL_CLONE` changed only NKE Git transport; CAPNICo fetched its public Git
source. Neither producer acquired a prebuilt provider image. Both used the
existing digest-pinned rootless BuildKit adapter and source-owned Dockerfiles,
with declared network access for base images and Go modules. This is not a
hermetic build or a claim that toolchain/base images were rebuilt from Git.

The build command exited zero. Retained lifecycle record:

own provider flags. No kubeconfig, credentials or cluster was supplied. This
proves startup/help only, not reconciliation or infrastructure provisioning.
