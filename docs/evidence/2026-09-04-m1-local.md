## What this record does and does not establish

This is **mechanics evidence for one local execution**. It shows that the compiled
`nke-v1` graph runs end to end on a laptop: pinned source in, hermetic container build,
OCI binary bundle, OCI publication root, push to a loopback registry, digest-checked
pull-back, and a recovered binary that runs and reports the version its upstream release
reports.

It is **not M1 completion**, and specifically:

- **Nothing was signed.** The signing lane ran in `mode: dry-run`. No `cosign` binary was
  executed, no key or OIDC identity was used, and no transparency log or Fulcio/Rekor
  instance was contacted. The signing and verification records state the argv a real
  signer *would* run; both carry `"dryRun": true`, and the verification record carries
  `"signatureVerified": false` and `"attestationVerified": false`.
- **The plan is `static-unqualified`.** Only `mode: cosign` can produce a
  `pipeline-attested` plan. The local run record's `qualification` is
  `unqualified-local-execution`.
- **The registry is a throwaway loopback registry** over plain HTTP with anonymous
  access. It carries no access control, no TLS, and no retention.
- **Nothing here is a validation vector, ReleaseSet, trusted-time checkpoint, clearance,
  or deployment authority.**

The remaining work is listed in [What remains for the GitHub run](#what-remains-for-the-github-run).

## Reproducibility and idempotency

The script was run repeatedly. Every run after the first reused the registry container and
the factory workspace and produced **byte-identical artifacts**:

- index digest `sha256:668cde31…` — identical across runs
- nkectl sha256 `eeb21f04…` — identical across runs
- plan digest `sha256:a4729426…` — identical across runs

The **predicate hash deliberately is not stable**: `runDetails.metadata.startedOn` and
`finishedOn` record when the run actually happened, so `predicateSha256` differs on every
run (`6316b361…` for the run quoted above, `23a4cd61…` for the run after it). That is
correct — a provenance statement describes one invocation. What must hold, and is checked
on every run, is that the recorded `predicateSha256` equals the hash of the predicate file
that run wrote.

Reproducibility here covers the build and packaging only. It is not a two-machine or
rebuild-from-clean-clone reproducibility claim; the source snapshot and toolchain image
were already cached locally.

## What remains for the GitHub run

This local exercise deliberately stops short of everything that requires infrastructure
that is not a laptop. None of the following is demonstrated here:

1. **Real cosign.** `mode: cosign` needs a `tools:` entry in `factory.yaml` pinning the
   exact archive and executable digests of a real cosign release. Those digests cannot be
   invented, so `definitions/nke-v1/delivery-github.yaml` is still `mode: dry-run`.
   Switching it on means: add the pinned cosign tool to `factory.yaml`, repin
   `factories.yaml`'s `definitionDigest`, then set `mode: cosign` and `cosignTool: cosign`.
2. **OIDC keyless signing.** No Actions OIDC token, Fulcio certificate, or Rekor entry was
   obtained. The `id-token: write` permission model on the rendered `sign` job is rendered
   and statically validated, never exercised.
3. **Repository provisioning.** `delivery-github.yaml` still names the placeholder org
   `example-nke` in both its target ref (`ghcr.io/example-nke/nke/nkectl`) and its identity
   regexp. A real run needs the owning org, a provisioned repository, and the
   `GITHUB_TOKEN` / package-write permissions to actually exist.
4. **`ghcr.io` transport.** Only a plain-HTTP anonymous loopback registry was exercised.
   Authenticated push over TLS to a real registry is untested here.
5. **A `pipeline-attested` plan.** Only cosign mode can produce one. Everything above is
   `static-unqualified`.
6. **Real CI execution of the rendered workflow.** The GitHub bundle is rendered and
   statically validated; no workflow was executed on GitHub-hosted runners, so the
   artifact upload/download and helper-permission behaviour is unverified in the real
   environment.
7. **`golangci-lint`** could not be run on this host: the installed binary is built with
   go1.26 while the module targets go1.27. Every other gate
   (`gofmt`, `go build`, `go vet`, `go test ./... -count=1`, `git diff --check`, and
   `factory generate --check` for both committed bundles) passed.

Until those exist, this document is what it says on the first line: local, unqualified,
dry-run-signed mechanics evidence.
