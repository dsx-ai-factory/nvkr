## Context

The evidence contract includes per-artifact SBOMs, external references for acquired artifacts, and deferred
vulnerability results. The set is deterministic, bound to artifact identity, and folds into the evidence bundle
(ADR-05). NVKR **produces** this evidence and owns no fleet lifecycle. Explicit local diagnostics have
lane **none (descriptive)** under [ADR-16 §6](0016-release-gates-and-digest-first-selection.md#6-passive-external-qualification-handoff--deferred-producer-protocol);
their reports cannot become publisher evidence or qualified receipts by being retained.

## Decision

### 1. SBOM identity: per-artifact + aggregate index

Emit a **deterministic CycloneDX SBOM per built artifact**, bound to that artifact's digest, plus an **aggregate
index** linking them. Serialization is deterministic — the serial number derives from the build/artifact
identity, with **no timestamps and no random UUIDs** — so documents are byte-identical across runs and validate
and ingest cleanly into stock scanners. Publisher-generated SBOM identity is also **mirror-invariant**: source,
toolchain, and prebuilt components use stable semantic identifiers plus their exact content pins. A repository
hostname, registry prefix, mirror key, or other relocatable acquisition locator cannot perturb the per-artifact
SBOM, its aggregate index, or ADR-05's publisher-evidence digest while the content and build identities are
unchanged.

This identity rule applies to evidence **generated by the publisher from its qualified producer report**. It does
not erase the location of separately acquired upstream evidence, which is an authenticated acquisition record
governed by §2: the transport locator is preserved so an auditor can retrieve or mirror the declared bytes, and a
separate digest authenticates those bytes. Moving that external reference changes the acquisition declaration
even when the verified payload digest is unchanged; relocating the publisher's build inputs does not change
locally generated evidence identity.

### 2. External evidence for acquired artifacts

**NVKE OS source-migration policy (proposed; candidate catalogs only).** Publicly
available component sources are compiled from exact reviewed Git pins. A failed
source build never authorizes fallback to a release binary. Where public source
cannot be established, preserve the existing exact prebuilt payload as an explicitly
documented source-availability exception, with its reason, per-platform digest and
evidence state. An internal Git source available to the operator may still be built;
its access restriction is not a prebuilt exception. Producer metadata/docs and
preparation logs identify these limitations without introducing a new schema field
or waiving evidence policy. A warning reports the declared exception only: missing,
inaccessible, unpinned or digest-mismatching bytes still fail closed. Source availability
is not automatically discovered or enforced by NVKR; reviewers must approve declarations
before maintained Definition integration. Existing evidence gates and the waiver
limitations below remain unchanged.

A `prebuilt` (no-compile) component carries a **verified reference** to the upstream's external SBOM/provenance.
The reference is a canonical transport location (HTTPS, OCI, or a mirror key); the content digest is a separate
exact identity, and the URL need not embed it. The referenced bytes **must hash to the declared digest or fail
closed**. Where no upstream evidence exists, the component declares an explicit **`evidence: none`** — never a
silent absence. That is **distinct from a Tier-4 exclusion** (`fromSource:false` plus a reason). One owning
schema defines the reference, consumed by both the acquire lane and the SBOM emitter.

`evidence: none` is an honest statement about an acquisition. It is **not evidence and never satisfies an
evidence-required promotion gate**. If release policy permits a missing evidence class, the exception is an
explicit, authenticated waiver naming the exact artifact digest, missing evidence types, policy
digest, reason, approver identity, and expiry. The waiver is policy evidence; it does not masquerade as an SBOM
or provenance receipt. Waiver issuance and release evaluation are not implemented.

### 3. Vulnerability-report determinism

A **shelled** Apache-2.0 scanner (grype/trivy — subprocess, never linked) produces a report naming the **scanned
artifact, the pinned scanner DB/policy version, and the build identity**, with **scan-time omitted**. The
DB/policy version is an **explicit pinned input**: a "deterministic" report only holds if the moving DB is
captured as a pin. A missing scanner **fails closed**, or is print-only under an explicit flag. A de-risking
spike covers this (below).

### 4. Advisory → affected-build boundary

Advisory generation and vulnerability scanning are outside the current product scope. The unused advisory,
scanner-argv and release-only vulnerability receipt implementations are removed. Pinned Syft composition
inspection in §6 remains implemented; it does not evaluate vulnerabilities or grant release clearance.

### 5. Qualified release evidence receipts — deferred

The maintained verifier recomputes same-process SBOM and provenance from exact qualified producer bytes and
compares their digests with an authenticated ValidationVector. External-reference acquisition still checks
exact payload bytes, schema and artifact subject before adding SBOM properties or recording explicit gaps.
These operations do not assemble release clearance. The unused external-evidence receipt adapters and release
waiver subsystem are removed.

A future qualified release gate must accept evidence only through opaque, exact-byte capabilities or the
signed receipts below. Same-process capabilities cannot be reconstructed from a decoded report or a boolean;
release policy must bind each input to its exact artifact, evidence type, schema and policy.

Any evidence crossing a persistence, process, registry, or organizational boundary uses a canonical,
digest-addressed receipt:

```
EvidenceReceipt {
  schemaVersion
  receiptType              # sbom | provenance | vulnerability | external
  artifactDigest           # exact subject bytes
  evidenceDigest           # exact canonical evidence bytes
  evidenceSchema
  verificationPolicyDigest
  producerIdentity
  verdict                  # accepted | rejected
}
```

The boundary-crossing receipt is detached-signed and authenticated against the trust policy for its
`receiptType`. The verifier recomputes both subject and evidence digests before issuing or accepting it. A
same-process capability MUST NOT be serialized as a substitute for this receipt; if it must outlive or leave its
issuer process, it is promoted into the signed form first.

A path, transport URL, mutable tag, untyped boolean, decoded report, or caller assertion such as `--verified` is
neither form. A qualified capability or receipt for one artifact, evidence document, schema, or policy cannot
satisfy another. Component-level references are not implicitly reusable across produced artifacts: every receipt
names the exact artifact subject it covers. The deferred ADR-16 release gate must consume only those capabilities or the
authenticated receipt set; raw evidence files remain the auditable payloads those receipts reference.

The removed evidence-gap waiver implementation used `nvkr.dev/evidence-waiver/v3`. Its digest family remains
reserved and nonminting; no current reader or issuer accepts this as clearance. A future waiver protocol must
bind component, build, artifact, builder-profile scope, status checkpoint, missing evidence types, policy,
approver and validity interval. It must authenticate its own schema and signer policy without reinterpreting
older signed bytes or reintroducing deployment roles.

### 6. Pipeline SBOM and acquisition scope

V1 emits deterministic CycloneDX documents per observed component artifact and an aggregate index through a
per-build SBOM node after terminal observation. Each subject is the runner-observed artifact digest; the index
also binds Build Digest. Resolved component declarations are frozen in the plan so the node needs no live
catalog. Adding those declarations or outputs changes canonical plan identity and requires regeneration.
The internal index uses `nvkr.dev/sbom-index/v2`; generated CycloneDX properties bind `nvkr:buildDigest`.
Replacing the former Recipe binding changes document identity; old evidence is not silently translated.

A Definition may select a catalog-pinned Syft executable through `sbomTool`. Both maintained NVKE
Environments require it. The graph then requires each observed payload and the acquired scanner as explicit
SBOM inputs. Missing payloads, missing scanner pins, unsupported formats, mismatched bytes, scanner errors and
empty inventories fail closed. Without `sbomTool`, ordinary declaration-only documents provide source
metadata; they do not claim dependency inspection. The separate full-disk profile pins its own scanner
and does not require a second catalog scanner selection; when both select the same native platform their
pins must agree. A catalog scanner for another platform does not replace the native inspection-profile pin.

The pipeline-attested M2 producer-provenance route explicitly selects `Environment.diskEvidence: build-provenance-v1`.
It retains the original held disk, exact producer results and authenticated transitive material handoffs,
and publishes source-bound per-component CycloneDX producer documents under the existing signed evidence
closure. These documents have no inspected dependency inventory and explicitly bind `nvkr:diskEvidence`
to `build-provenance-v1` and `nvkr:diskInspection` to `not-performed`. The signed release disk binding carries
the same evidence mode. Producer integrity, provenance, every component slot and release completeness remain
mandatory. This is pipeline-attested producer evidence, not an inspected inventory or qualified evidence.
The [approved October 12 M3 MVP scope](https://nvidia.atlassian.net/browse/NKX-15959?focusedCommentId=25021826)
retains this producer-only disk evidence. Deep disk/content inspection and material-to-filesystem reconciliation
are deferred hardening under [NKX-18052](https://nvidia.atlassian.net/browse/NKX-18052), outside MVP completion.

Under the current scope directed by the user, embedded-component declarations are optional: omission is not
applicable, while any authored declaration must match its referenced upstream manifest at the pinned commit. This checks source-metadata consistency only;
it does not account for effective build customizations or inspect installed disk contents. Source, patch,
configuration and material bindings remain mandatory in the producer-evidence contract.
The native ARM64 route and authored outputs are an implementation extension, not a milestone-scope approval.
Every disk actually selected by a Definition retains exact producer/material, delivery and evidence obligations;
the AMD64 product floor cannot waive ARM64 completeness. Organizational ratification of the ADR set remains separate.
Historical signed documents may retain the earlier `deferred-m3` scope token; do not rewrite those bytes or
interpret that token as inspection evidence. The strict inspected-evidence contract below remains available
only under its separately admitted capability and evidence policy; M3 success cannot imply it was exercised.
Unknown modes fail closed; an omitted producer mode retains the strict contract. Document validators check the
declared mode and reject invented inspection claims. Consumer acceptance is separately controlled by
`VerificationPolicy.minimumDiskEvidence`, included in the policy digest. For `pipeline-attested`, an omitted
value defaults to `build-provenance-v1`, admitting producer-only evidence and stricter inspected evidence;
explicit `strict` rejects producer-only evidence. Qualified policy defaults to strict and rejects the
producer-only minimum. Producer metadata cannot lower the consumer's selected minimum. Mode changes
affect Environment/Plan and signed release metadata, not raw payload identity. Only the explicit native ARC
publication route admits this mode.

The strict `disk-image` inspection route requires a full CycloneDX inventory whose subject is the
exact delivered QCOW2 payload digest. It combines an authenticated trace of every fetched or built material with
read-only inspection of the final disk, then reconciles both views. The material collector, disk codec/inspector,
and package scanner are pinned tools and explicit Plan inputs. Missing tools or trace members, unreadable
filesystems, unsupported encryption, scanner failure, or disagreement fails closed at admission or inspection.
A catalog declaration alone supplies neither inventory nor publication authority; the narrower producer-provenance route above
requires authenticated live producer evidence instead of an inspected inventory.
The authoring schema alone grants no disk evidence. The full-content operation selects an explicit
Environment-native `diskInspectionProfiles` entry frozen in the Plan: the complete OCI image, inspector,
codec, guestfish, Syft and dpkg-deb executable pins, CPU/RAM ceilings (at least 2 GiB for the appliance), scratch capacity minima,
filesystem expansion bound and wall-time limit. Changing this observation profile changes Environment/Plan identity rather
than the logical producer Build. The pinned tools own disk/filesystem, package and OCI grammars;
NVKR projects their observations and does not execute guest programs or package installation scripts.

The original held Packer artifact retains its declared acquisition carrier before producer cleanup.
The runtime owns capacity admission, snapshot creation, bounded offline content scanning, snapshot
closure and permit release as one registered operation. Factory retains the original Run permit
through inspection of the disk, base installer, staged material closure and captured guest APT archives.
Queueing and profile/trace admission remain bounded to ten minutes. The selected authenticated profile's
wall-time limit multiplied by the exact content-operation count (root, other trace members and the one
complete acquisition carrier) sets the scan/recheck deadline from the original operation start. An earlier
caller deadline or Run closure still cancels the entire join; recursive scans do not add allowances.
Reconciliation rejects absent input classes and installed package identities absent from those inspected
inputs. The exact captured package bytes are separately read by pinned dpkg-deb before source-reported
metadata is accepted. Owner-issued content classes distinguish filesystem package databases, container
inventories and held Debian archives: a container database cannot justify an installed host Debian package.
The native Syft adapter retains real/access-path coordinates through admission. Its recursive database
cataloger can find unpacked or containerd snapshot roots; those nested package databases return
`CodeEngineCapability` with a distinct diagnostic until a separate held root/container observation exists.
This gate applies to filesystem, archive and container scans through the shared native report decoder. No path-based container
identity is invented, no package is silently dropped, and this refusal does not establish functional
nested-storage reconciliation. Scanner locations remain descriptions, not installed-origin authority.
Correspondence is checked before public document deduplication; those internal classes do not assert
installed origin or package ownership. Loose-file hashing observes bytes, not their derivation.
Unknown package versions remain unknown in descriptive inventory. Final material correspondence requires
an exact observed version: equal names with unknown versions do not prove identical package content.
Per-material mixed scanner/package-reader/file-walk documents use the descriptive `disk-content/v1`
inspection method, not `syft-cyclonedx/v1`. Only the final correspondence operation uses
`disk-reconciled/v1` with an `operating-system` subject. File dependency inventories are admitted only
for these per-artifact disk methods and the separately scoped `archive-content/v1` method below,
not ordinary Helm/Syft dependency documents. Source declarations
cannot relabel the inspected disk subject. This is descriptive vocabulary validation: neither a subject
type nor a method string restores a runtime receipt or grants publication authority.

The implemented QCOW2 reader exports libguestfs's inspected, mounted filesystem tree, not an independently
enumerated inventory of every filesystem extent. Unmounted or unrecognized content is not proven covered.
The installer reader supports ISO9660 and its recognized SquashFS payload; a generic raw material is not
thereby known to be a base installer. The exact authenticated root consumer's declared `installer-iso`
edge selects that purpose; raw output type alone does not. Transitive and other raw ISO inputs retain
staged `installer-content` inspection and per-component documents, without satisfying the mandatory
base or supplying base-filesystem package correspondence. Both operations use the existing ISO/SquashFS
reader: other raw formats remain unsupported at its format boundary rather than disappearing from the
trace. Nested image discovery recognizes bounded gzip or plain tar
contents, not image format from a filename. The pinned Docker decoder requires an unambiguous Docker
manifest; OCI layouts reuse the existing safe transport extractor and complete offline closure verifier.
Every accepted image is inspected, while foreign platforms, unsupported descriptors, missing or extra
blobs and mixed OCI/Docker markers fail closed without partial inventory.
Top-level `oci-image` disk materials use the same complete-closure owner, but admit only plain,
uncompressed OCI layouts no larger than the selected filesystem bound. Docker-marked, gzip,
`./`-prefixed, foreign/unknown-platform attestation and malformed/oversize carriers fail before
inventory acceptance; mixed Docker/OCI markers return `CodeEngineCapability`, matching nested discovery.
Each unique image is scanned through a bounded private Docker-archive projection after every
descriptor/configuration matches the consumer platform, with the observation bound to the original held
carrier and closure revalidated afterward. Direct OCI copies and sequential per-image projections are
bounded separately, not charged to cumulative expansion bytes; shared member/image limits still apply.
The 16,384-component report ceiling applies before downstream public deduplication, so shared-base
inventories can fail closed even when their unique inventory would fit.
Real NVKE material complexity, cold-cache timing and full-matrix inspection remain unverified.
Modern mixed Docker-save
archives, OCI member names prefixed with `./`, and OCI indexes carrying foreign/unknown-platform
attestation manifests are unsupported; an attestation descriptor is not silently discarded as image evidence.
The maintained NVKE preparation at `b30117c25b2dcdf6c16021dae88a2eafdafcae61` uses pinned crane
Docker-archive pulls followed by GNU-tar/gzip repacking, not modern Docker-save mixed layouts. This
source inspection does not establish that retained prepared archive bytes were fully scanned. One operation shares its
filesystem-byte expansion allowance across sibling archives and Debian exports, with 16,384 recursive
members, a shared 256-image allowance and bounded nesting. Each selected Docker manifest entry charges
that image allowance before digest deduplication; each unique OCI image digest charges it within its layout.
Decoded root image markers select that inspection before member/expansion charging; ordinary gzip/tar,
including empty or corrupt filename candidates without such a marker, retains only its outer file hash.
The marker probe streams under the operation deadline, without charging the image expansion/member
allowance or imposing a separate probe byte limit. Repeated OCI image digests are scanned once per layout,
not across material carriers, but every descriptor/platform is checked; the pinned layout
accessor still reparses its bounded index for each unique image/child lookup. Ordinary tar contents retain their outer file hash;
other compressed formats have no nested-image discovery. These adapters are contract-tested with
controlled archives; complete native Syft discovery remains unexercised. The root file inventory
retains actual exported paths and the exact outer archive hash;
files inside cached Debian archives, Docker archives or SquashFS payloads are not presented as
invented installed paths. Their discovered components carry descriptive `nvkr:containedIn` values
binding the immediate held carrier path and digest. Repeated public package identities retain a
sorted canonical string list of those carriers; no recursive ancestry, installed origin or package
ownership is inferred. A contained payload's file inventory is not an independent root-file inventory.
Every uncontained non-file component carries `nvkr:observedAtSubjectRoot`, including when its public
package ref also has contained observations; it is not an installed-origin claim. `nvkr:materialSubjects` matches only
top-level regular-file hashes in each material observation. Nested Debian/SquashFS/image file digests
do not currently participate in that file correspondence, and absence of the property is not non-correspondence proof.

The process-local reconciliation receipt binds the original Run, named output, complete Plan, Build,
QCOW2 digest/size and admitted inspection closure. Export revalidates those owners before copying the
exact disk and returning its deterministic CycloneDX document. Descriptive documents, decoded receipts,
equal-byte sibling Runs and shallow copies after owner closure cannot restore authority. The full-content
helper, semantic reconciliation and private scratch paths are implemented. Contract tests cover modeled
reconciliation observations, selected admission/decoder failures, private issuer-core success for both
consumer architectures and export-owner revalidation. The issuer tests keep complete Plan, original Run,
payload selection and material-trace checks concrete, while modeling stopped scan/profile observations;
the public wrapper still requires the actual Packer capability and opaque inspection operations. Those
tests do not establish full helper discovery. A separate opt-in [controlled ELF-protocol test](../../pkg/nvkr/factory/disk_evidence_runtime_linux_test.go)
targets public producer/inspection owners, receipt issuance, exact export, six negative issuer rows
and the concrete memory-profile guard; it is not actual Docker/Packer/guestfish/Syft discovery.
Native AMD64 public positive issuance, complete native NVKE content runs, original live NVKE strict joins,
strict inventory publication and strict production acceptance remain unexercised.
Complete inventory documents are bounded to 32 MiB, composition helper reports to 16 MiB,
and signed SBOM transports to 64 MiB. These document/bundle policies apply to every SBOM subject,
not only disks; malformed or oversized SBOM evidence returns `CodeVerifyFailed` (exit 22) before
cosign work. Provenance independently retains its 4 MiB predicate bound and `CodeProvenanceMissing`
(exit 45). Sigstore upload/service acceptance at the larger inventory sizes is not established by local tests.
Diagnostics and generic OCI records retain their independent
8 MiB limits. A controlled 50,000-file projection measures approximately 9.15 MB of report and
20.20 MB of CycloneDX; this is not Ubuntu discovery or native execution proof. The 200,000-file
structural ceiling does not guarantee every such inventory fits the byte limits; oversized complete
evidence still fails without truncation. Full-content admission charges four overlapping report
copies for the increase over the diagnostic allowance. The conservative
simultaneous export/RAM budget is an admission condition, not evidence of runner capacity or reservation.
Disk-backed scratch authenticates an empty attempt-owned daemon volume, its local driver/options and
observed free space before streaming. It does not observe `nosuid` or `nodev` mount flags on that volume;
the memory-backed route explicitly requests both. The non-root consumer drops all capabilities and
requests no-new-privileges, while the fixed ownership preparer has only CHOWN. These controls do not
justify claiming equivalent mount-flag enforcement or a provider-owned storage quota.

Inspection progress is a separate, non-authoritative channel. The inspection helper emits only closed phase/event
names, elapsed milliseconds and bounded numeric counters; stdout remains the complete report. The host rejects
unknown diagnostics and, for full-content composition inspection, enriches accepted records with its original held subject's digest and content kind.
Records are bounded to 512 bytes, the sanitized retained log to 32 KiB and forwarded records to 512 per helper
operation. Parsing has a separate per-helper ceiling of 5,441,310 prefixed candidates, including malformed JSON.
This conservative emission bound covers the outer filesystem and 32 installer members, each admitted archive's
16,384 selected-member and 256 image limits, fixed phase pairs, two records for each nested OCI image's scan and
two for its transport, and the start preceding an excess-member rejection.
After the ceiling the receiver drains without further framing or JSON parsing, rejects the inspection and retains
its last accepted phase. This volume ceiling does not truncate or accept a partial report.
Rate limiting and truncation never hide the last accepted phase. Guest paths, raw tool output,
arguments and credentials are not retained. A non-timeout terminal error may contain a quoted, 4 KiB-bounded
copy of unrecognized stderr; this error-only copy never enters the collector or uploaded diagnostic file.
Sampling, record caps and byte eviction mark the snapshot as truncated. `filesystem-staging` measures the
private filesystem snapshot copy, `filesystem-probe` the ISO type check and `scanner-transport` the scan-carrier copy.
`member-walk` measures archive traversal, while `nested-scan` identifies a selected member scan; depth and ordinal
distinguish installer-member re-entry and nested payloads. Diagnostic depth is bounded to four, including
the installer filesystem plus the existing recursive-member depth; inspection recursion limits are unchanged.
`export-startup` covers appliance startup and auto-mount until the
first exported bytes; it does not separately measure those preceding operations. Timeout diagnostics do not
issue an inspection receipt or change the primary error. Timing is excluded from content-report and SBOM identity.

The helper checks the actual cgroup-v2 CPU, memory and process-count ceilings before reading the subject.
The leaf must exactly match the frozen CPU/RAM values and the launcher's 256-process ceiling; unknown,
unlimited, malformed, changed or tighter visible ancestor limits fail closed. This authenticates kernel
limits visible through the current cgroup mount, not a reservation, hidden ancestor capacity, provider
allocation or a hosted identity boundary. The generic APIs do not by themselves connect a production disk
compiler, packaging consumer or publisher.

The diagnostic guest package capture schema `nkd.dev/package-acquisitions/v1` has scope
`apt-pre-install-pkgs` and target `amd64` or `arm64`. Its canonical JSON manifest is the first USTAR member,
followed by nonempty, unique package members in digest order with exact digest-derived paths and sizes.
Limits are 16,384 packages, 1 GiB per package, 8 MiB manifest, 8 GiB archive, and 1–32 bounded raw repository
locations per package, each at most 4,096 bytes. The owning held-archive verifier checks member-byte
correspondence without extraction; package display metadata and locations remain source-reported descriptions.
Header metadata and member padding are opaque digest-bound bytes, not canonical package evidence. Capture
settings belong to the selected producer configuration. The [capture contract](../nvke-os-acquisition-contract.md)
describes the unpinned NVKE candidate. The generic collector binds a selected carrier to its original
Run/QCOW2; native capture coverage and repository-origin authentication remain unverified. Neither this
diagnostic observation nor its zero-value description authorizes production or substitutes for the full
exact-QCOW2 inventory required above.

The optional local installed-package diagnostic uses a caller-selected, already-local
exact image on its native Linux architecture. Its fixed launcher is unprivileged
(UID/GID 65534), networkless, read-only, drops all capabilities, disallows requested
mounts/devices/credentials, enables no-new-privileges and init reaping, and bounds
resources and the operation deadline. Native Podman commands suppress automatic
`mounts.conf` inputs on create, start and owned cleanup; an unsupported override
fails closed. The runtime executable, daemon configuration, OCI hooks and host
kernel remain trusted. Held subjects and tool bytes are rechecked; the returned
installed-package inventory carries the runtime-reported image identity, not a
repository-approved runtime pin or provider-isolation receipt. This diagnostic
does not authorize full-disk SBOM, production publication or qualification.

The exact-QCOW2 reconciliation proves the composition observed in one exact disk; it is not a reproduction comparison.
Matching dependency digests, installed-package sets, selected file hashes, or SBOM documents across two Runs can
support content validation and diagnose drift, but cannot mint `Reproduced` when the qualified artifact subject
differs. Each different QCOW2 digest remains a new Artifact identity with its own SBOM subject and production
provenance. Independently reproduced or acquired materials keep their own evidence relationships without
upgrading the disk that consumed them.

A narrower, opt-in local installed-package diagnostic may join the factory's live staged-material trace to
read-only inspection before the issuing Run closes. Factory accepts only its original held Packer output and
an admitted concrete inspection runtime. The runtime binds an exact OCI closure and inspector/codec identities;
capacity admission precedes the additional anonymous disk snapshot. The runtime owns admission, snapshot
creation, scanning, snapshot closure and permit release as one cancelable, joined operation; no borrowed
snapshot or capacity reservation escapes to a caller. The package-issued, process-local result
binds the original Run owner, named output, Plan, Build, QCOW2 digest/size and inspected runtime/tool bytes.
Equal subject bytes or Build identity cannot authorize reuse by a sibling attempt. Closing the Run cancels
active inspection, joins cleanup and revokes live use, including shallow receipt copies. Historical installed
metadata remains inspectable but cannot be serialized and restored as authority. Omitting this opt-in does not
claim inspection. Opting in makes successful inspection a condition of local Run completion: a failed scan,
subject check or cleanup fails the Run and discards its uncommitted disk export. A failed Run exposes no
installed inventories. This prevents a requested inventory from being paired with undelivered or differently
observed bytes; it does not grant publication or qualification authority. This diagnostic is not the complete acquisition trace, reconciliation, full CycloneDX
document, disk publication gate or qualification described above.

For binaries and OCI image exports, the SBOM owner invokes the pinned scanner as an owned, bounded subprocess
inside the offline utility container. Inputs are held and checked against producer digests. Syft's file resolver
requires a pathname, so binary inspection uses a private read-only copy of held bytes and checks it again before
acceptance; ordinary acquired-image inspection consumes the held descriptor directly. Strict disk OCI
materials instead use the complete-closure/private-projection contract above. Scanner configuration and environment are
isolated. The report is projected into deterministic component names, versions and package URLs. File-location
records, temporary paths, timestamps and scanner-generated IDs are excluded. Scanner executable identity is
recorded separately. Unknown versions remain unknown; they are never filled from unrelated module tags.

The separate `InspectDebianArchiveMetadata` diagnostic always uses the constant private snapshot name
`subject.deb`, independent of the caller's filename. The caller's basename is not copied, and the extension
supplies no format or identity proof. Syft parses a private read-only copy of the held bytes, rechecked against
the digest after scanning. Its result uses the diagnostic method `syft-debian-archive-metadata/v1`, which
dependency SBOM attachment and serialized BOM validation reject. Package/control metadata cannot become
payload dependency evidence. The ordinary path-based `InspectDependencies` and held-only
`InspectHeldDependencies` APIs retain hint-free host-file scanning; OCI scanning is unaffected.
The Syft v1.51.1 discovery premise is version-specific: rerun the opt-in regression when changing either
the factory catalog Syft pin or the Syft pin in `toolchains/nvkr-disk-inspect`.

Factory callers retain the ordinary dependency API; no maintained factory output invokes the separate
Debian metadata diagnostic. Factory SBOM nodes inspect producer bytes before APT wrapping, and the existing
executable/APT routes do not preserve a source-created Debian package. The diagnostic does not admit such
a delivery route. The authoritative Debian material reader remains digest-pinned
`dpkg-deb`, with platform checks and bounded payload expansion in the disk owner. A standalone Debian
delivery format, declared-format propagation through path and held APIs, and payload coverage through that
owner remain deferred. This diagnostic does not validate target architecture, preserve a source package,
enable direct APT publication, or prove installation.

For Helm source archives and exact acquired archives selected as Helm outputs, a generic manifest reader inventories bundled `Chart.yaml` declarations and chart
dependency declarations/locks. It never executes
installation scripts or fetches external charts. Bundled charts and locked references are
distinguished; a locked reference does not establish the referenced chart's transitive contents. These
documents describe the observed archive before image-binding/package transformations. Raw artifacts
are admitted to this reader only when the compiled output, acquisition producer, and resolved component
all identify the same acquired Helm chart; other raw formats remain unsupported.

Generic source tarballs selected as assets in an executable output use the explicit
`archive-content/v1` method. The exact resolved component must declare `tarball`,
belong to that output and have no Helm packaging declaration. This selection is
compiled from declarations, never guessed from a filename or used as a fallback
after a Helm failure. Other output formats retain their existing inspection paths.
The archive reader uses the standard library's tar/gzip decoders over held bytes
checked against the producer digest. It hashes every regular member without
extracting files or executing a scanner. A document has an exact file subject,
the original tarball output-type binding, nonempty file components with canonical
relative member names and SHA-256 hashes, and no scanner identity, package URLs
or inferred versions. This describes archive contents, not package discovery,
installed contents or transitive dependency coverage.

The reader bounds expansion to 256 MiB, individual members to 64 MiB and returned
member entries to 65,536. The expansion budget includes metadata headers and padding. It checks
the entire compressed stream and rejects malformed data, unsafe or duplicate
paths, conflicting file/directory paths, links, sparse and special files, nonzero
trailing content and archives with no regular members. Reads remain cancelable.
The serialized document validator and the shared packaging/finalization join
preserve this method's scope; an archive inventory cannot satisfy Helm metadata,
Syft package discovery or reconciled disk requirements.

Per-artifact documents keep the subject in `metadata.component` and use `components` for discovered packages
or declared chart dependencies; the explicit archive method instead records member files.
Stable `bom-ref` values distinguish versions with the same name. Root dependency
edges cover the inventory; they assert artifact inclusion/reference, not invented package-to-package call graphs.
The index binds the populated document digest. Hosted finalization rejects missing dependency inventories and
wrong subject/scanner bindings when inspection was requested. Package discovery and descriptive archive inventory are not vulnerability scanning
or qualified reproduction. It does not claim dependencies absent from artifact metadata can be discovered.

SBOMs assert composition. Packaging requires each exact output's SBOM set and producer record
as explicit graph inputs. The shared packaging/finalization validator checks exact output, Build Digest, subject, document
and requested scanner identities. Per-build indexes are internal handoffs only. The authoritative release index
owns published evidence membership (ADR-20 §6); every required document is referenced once in its owning artifact repository and carries explicit
subject kind/digest and stage. Byte-identical inventories may be published once after every independent output
handoff passes validation. Publication deduplication cannot replace an output's missing producer record or evidence.
CLI evidence covers the built binary. Native-image evidence targets its exact manifest and records the verified
OCI-export input used by the scanner. Helm source evidence remains bound to the source archive; a separate
packaging inventory reads the final bound archive after image binding and checksum refresh. That inventory
covers chart declarations/references, not an execution or scan of referenced image contents.

Each production document is published only inside a CycloneDX attestation in a Sigstore v0.3 bundle.
An explicit pre-publication job creates and verifies those bundles with the configured workflow identity,
issuer and transparency policy. Bundles are OCI referrers in their owning output repositories; an association
to the final Helm manifest never changes the source-archive subject of source evidence. The release signature
covers their exact manifest/blob identities and the canonical document digests through release metadata.
Independent consumers verify the bundle's statement subject and signature. No extra signature on the SBOM
wrapper or raw published document is required.
Consumers derive mandatory evidence slots from output membership and reject missing, duplicate, substituted
or unbound documents and stages. Finalization compares the published documents with the validated source
handoffs and final package inventory. The current consumer has no old-layout fallback. This establishes
pipeline artifact-publication evidence, not qualified receipts, vulnerability clearance or signed completion.

SBOMs remain `static-unqualified` in dry-run. Generation alone is no signature or reproduction proof. Acquired components retain `evidence: none` unless pinned upstream evidence is declared. V1 does not
verify upstream signatures/provenance on acquisition. Vulnerability scanning stays outside v1.
Curated/embedded aggregates use dependency edges from aggregate to members (ADR-10/22).

## Consequences

**Positive**
- Every built artifact has deterministic, digest-bound SBOM and (via ADR-09) provenance an auditor can recompute.
- Acquired artifacts are honestly marked — verified reference or `evidence: none` — preserving the
  from-source XOR prebuilt XOR exclusion trichotomy.
- Promotion distinguishes present evidence, absent evidence, and an explicitly authorized waiver without
  converting absence into success.
- Vulnerability results are reproducible when the DB/policy is pinned, and consumable by stock scanners.

**Negative / costs**
- Vuln-report determinism requires provisioning and mirroring a pinned scanner DB/policy — an infra dependency
  for air-gap.
- External-evidence conventions vary per upstream; some references degrade to `evidence: none`.
- Persisted and cross-boundary receipt issuers and waiver approvers require explicit trust-policy roles and
  key-rotation procedures; same-process capabilities require careful private-state and mutation-isolation tests.

**Neutral**
- All evidence serializes through the canonical codec (ADR-01) and feeds the evidence bundle (ADR-05).

## Alternatives considered

- **A single aggregate SBOM keyed on the build.** Rejected — FR-15 requires per-built-artifact SBOMs; it blocks
  artifact and inventory consumers.
- **Link a scanner library.** Rejected — staying Apache-clean requires shelling the scanner.
- **Maintain a released-build index to map advisories to the fleet.** Rejected — it crosses the
  produce-vs-operate boundary.

## De-risking spikes

1. **Vuln-report determinism** — two runs over a fixture SBOM plus a pinned DB snapshot are byte-identical,
   offline.

## Follow-ups

- **ADR-05:** the SBOM and provenance digests are the per-artifact evidence rows the bundle aggregates.
- **ADR-09:** provenance is the companion evidence per built artifact.
- **ADR-16:** derives the exact required receipt types from Inventory plus promotion policy, and rejects
  `evidence: none` unless an exact, unexpired waiver receipt is authorized.
- **ADR-22 §7 / ADR-10:** the aggregate SBOM's dependency graph points from an aggregate to its members when
  they come from a curated pin set or from a `wrapped-build`'s `embeds` (aggregate → members), rather than
  presenting them as unrelated peers; the CycloneDX representation of that edge is this ADR's to fix.

## Acceptance evidence

Current module evidence in `pkg/nvkr/sbom/*_test.go`, `pkg/nvkr/attest/*_test.go`, and
`pkg/nvkr/catalog/prebuilt_test.go` covers deterministic documents, prebuilt declarations, publisher evidence
equality across online/mirror transport relocation, same-process exact-byte qualification, HTTPS-reference byte
and subject verification, and mutation rejection. It does not prove vulnerability scanning, waiver evaluation,
release clearance or signed cross-process receipt publication.

Acceptance additionally requires a boundary fixture that promotes same-process capabilities into canonical
signed receipts, publishes and reloads them, recomputes the exact artifact/evidence bytes, rejects receipt-type
and signer-role confusion, rejects replay to another artifact or policy, proves `evidence: none` fails an
evidence-required promotion, and proves only an exact unexpired waiver signed by the configured waiver authority
permits the documented exception.
