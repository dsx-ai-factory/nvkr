# Combined NKE M2 candidate inputs

This Definition joins the existing CLI, controller, deployment-chart and native non-FDE OS selections,
with separate AMD64 and ARM64 disk outputs. CLI/controller/chart selections reuse the maintained catalogs.
The OS catalog is an explicit source snapshot with native KVM selection and retained APT capture enabled.
It also acquires AMD64 operator executables, the formal v1 operator target, from the official Helm and
Kubernetes release assets.

The human-selected external-image mode is the pinned NKE deployment values at
`33fb71b2f4224b470ebc628a9165fc4b92870406`, not chart defaults. `image-catalog` acquires twelve
non-test runtime images (PostgreSQL, eight SPIRE images and three Temporal images), each with actual
AMD64 and ARM64 native manifest pins generated by `catalog pin-artifacts`. The Definition contains
34 named outputs: the original ten plus those 24 native image members. Charts remain configurable;
no unsupported deployment-values field is added or inferred. Optional test images and the separately
owned external NKE-image checkpoint are documented in the input evidence map.

The PostgreSQL and SPIRE Bash source references are digest-pinned upstream indexes.
Their four native output rows retain real child-manifest pins, but executable graph
lowering currently rejects them with `CodeUnverifiedRef`: pin maintenance authenticates
index membership without retaining an execution-authorizing membership receipt.
No index digest is dropped or replaced to bypass this gate. The other twenty
native acquired-image graphs compile; that is not image publication or acceptance.

The operator catalog selects Helm 4.1.4 and kubectl 1.36.3 from the pinned NKE kubeadm-distribution lock:
`dsx-ai-factory/nke@b30117c25b2dcdf6c16021dae88a2eafdafcae61`,
`os-image/packages/kubeadm-distro/lock/amd64/v1.36.3.lock`.
Their downloaded transport hashes match that source-owned lock. Helm's archive and selected executable
have distinct pins; the delivered file is `helm`, not its tar archive. Kubectl is a raw executable.
The local lock is generated with the existing catalog pin/bump command, not hand-authored.

The four NKE OS/material sources are machine-pinned to that exact commit using `catalog pin --commit`.
NKE #1211 is still open and unmerged at that head; the pin is a review candidate, not
source-owner release approval. Exact commit acquisition does not establish reachability
from a protected/default branch. Publication must not be treated as approved until that
source-review gate and the independently missing execution/profile gates are resolved.
Its source-owned direct-Packer contract receives `capture_apt_acquisitions=true` and exports
`non-fde-apt-acquisitions.tar`, which the catalog declares through `packer.acquisitionArchive`.
The selected material projection binds `image-inputs` as `archive` and `installer-iso` as `disk-image`
under `nke.dev/os-image-materials/v1`; every selected material and disk target retains its own architecture.

This is a candidate Definition, not completed M2 acceptance. The production target Environment reuses
the existing registry credential, namespace, source access and workflow signing policy. Native disk
execution classes and measured native inspection profiles are absent, so admission must fail before a Run.
OS toolchain digests remain the inherited local runtime identities, not approved published OCI pins.
The inspector and Packer source locks retain their outstanding publication approval gates.
The candidate Environment selects Podman through the existing typed runtime controls;
it declares no storage-driver field or ambient runtime-variable workaround. Storage behavior
is admitted and observed by the existing runtime owner. The historical explicit-VFS probe
is diagnostic evidence, not this Environment's configuration or production approval.
Default-owner semantics do not supply absent execution-class or full-inspector profile authority.
A complete generated Run must admit execution, inspect and reconcile both
disks, generate exact-subject evidence, publish/sign all required outputs, and pass independent consumer
verification before these inputs can be called an accepted M2 release.

The [input evidence map](../../docs/m2-input-evidence-map-2026-10-05.md#native-acquisition-build-and-measurement-commands)
lists repository-owned native preparation and measurement commands, their current
source-review gates, and the missing production inputs. The inspector's source
README gives separate AMD64 and ARM64 assembly commands; no source lock currently
supplies either approved published native toolchain closure.
