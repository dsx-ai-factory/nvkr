Read the recipe. Name the deliverable.

Keep reusable production instructions separate from the outputs your product promises.

A component is a catalog key with a reusable producer recipe. An output is a deliverable the Definition requests. An artifact is the actual file, image or package produced.

The catalog makes tools available

app-cli is the application tool. config-cli is the configuration tool. Each entry declares how to build or acquire it.

The Definition chooses what ships

client-bundle selects app-cli. admin-bundle selects both. Adding a catalog entry alone does not add it to a deliverable.

Prepare the metadata layout for offline browsing

With the GitHub CLI authenticated, download the Run’s metadata package before presenting. This small carrier contains the release metadata and evidence documents, without artifact payload layers. Keep RELEASE_REF from the command above.

One download, then repeatable offline browsing
DEMO_METADATA=$(mktemp -d)
gh run download 37736529644 --repo dsx-ai-factory/nke-recipes \
  --name nkd-package-release --dir "$DEMO_METADATA/download"
bin/nkdctl transport-unpack \
  --archive "$DEMO_METADATA/download/package-release.tar" \
  --root "$DEMO_METADATA" --path .nkd/factory/packages/release
bash demos/demo-team-release.sh --reference "$RELEASE_REF" \
  --layout "$DEMO_METADATA/.nkd/factory/packages/release" \
  --output nke-node-image-arm64 --mermaid

The fresh directory preserves the downloaded carrier and validated extraction. Subsequent browse calls can reuse the same --layout path offline. Each call validates the metadata closure before filtering; extraction alone does not verify the release’s signatures or payloads.

What do the signed statements establish?

RecordQuestion it answers
SBOMWhich software is described for this exact subject and stage?
ProvenanceWhich process and inputs produced this artifact?
SignatureWhich workflow signed this exact artifact or statement?
Consumer policyDo we accept that signer and the stated evidence scope?

A signed attestation authenticates a statement about exact bytes. It does not claim ownership of the software.

Verify using your accepted policy · Linux or macOS with Docker

The consumer script runs directly on Linux and uses its pinned Linux Docker image on macOS. Supply a digest-pinned static Linux cosign executable and the signer/issuer policy your team accepts.

Independent consumer verification
bash scripts/demo-release-consumer.sh \
  --reference "$RELEASE_REF" \
  --identity "$ACCEPTED_BUILD_IDENTITY_REGEXP" \
  --issuer "$ACCEPTED_OIDC_ISSUER" \
  --cosign "$COSIGN_PATH" --cosign-digest "$COSIGN_DIGEST"

For private registry access on the macOS route, supply --registry-config with inline Docker auth; use --anonymous for public access. The supported pipeline-attested / artifact-publication scope authenticates exact published contents and their required signed evidence. It does not establish qualified reproduction or deployment readiness.

The macOS Docker consumer was exercised successfully against this run’s single-output releases-nkectl@sha256:768b0ef67a09649465a66ff360eb44e74237a22c66da34bcee961247f06bd4d9 publication under the accepted main-workflow policy. That result covers the CLI publication, not the combined release or disk payloads.

Historical v3 compatibility

The earlier Run 37533806963 used publication-root v3. Current NVKE Recipes requires publication-root v4, whose root binds the canonical Plan digest. A successful verification may emit nkd.dev/release/v3; that separately versioned consumer description is compatible with the v4 stored root. Retained v3 graphs are readable presentation data; replaying that old root requires its separately built historical PR #108 CLI. Do not pass the old root to the current consumer.
