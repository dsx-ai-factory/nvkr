Prepare once

Build the CLI. Keep the browser open.

Run terminal commands from the repository root, with the Go patch specified in .go-version. This walkthrough uses PR #108 head 00c71385; the featured pipeline ran at its separately recorded source commit.

Repository root · one-time preparation
GOTOOLCHAIN=local make build

The scripts pause at checkpoints and print a fresh export directory. Use --non-interactive to skip pauses, or --out NEW_DIR beneath an existing parent. An existing output directory is rejected. To reuse a PR-head binary, set NKDCTL_BIN to its absolute path.

Catalog and OS planning need no Docker or source checkout after the CLI is built. Live release browsing needs Python 3, registry access and suitable existing credentials. The saved browser views work offline.

01

Name the components. Choose what ships.

The catalog says how to build or acquire each component. The Definition groups selected components into named outputs. The Environment supplies execution and publication settings.

3–5 minutes · optional replacement lab belowReturn to slide 3 ↗

Use two commands as a running example: doctor is a health-check command and status is a status command. Their catalog entries contain the build instructions. An output is the deliverable that includes the commands you select.

Catalog: reusable components

  • doctor — instructions for producing the health-check command.
  • status — instructions for producing the status command.
  • doctor-alt — a separately named alternative health-check producer, available for explicit selection.

The authoring lab uses small shell scripts as stand-ins for these commands. They print fixture messages; this example does not perform real health checks.

Definition: named outputs

  • diagnostics includes doctor.
  • tools includes doctor and status.

Both outputs select the same component name, doctor. They remain two independently required deliverables.

Definition excerpt · two of the authoring lab’s seven outputs
outputs:
  - name: diagnostics
    components: [doctor]
  - name: tools
    components: [doctor, status]

This excerpt omits platform, format and the other outputs. The complete input is docs/examples/authoring-lab/definition.yaml; component recipes live in docs/examples/authoring-lab/catalog/registry.yaml. The replacement lab below uses these exact names.

Optional hands-on lab

Same component name, different instructions.

Return to the two outputs above: diagnostics selects doctor; tools selects doctor plus status. Initially, both use the same catalog recipe that builds doctor from source.

An overlay supplies a complete replacement recipe for the same component name. In this lab, doctor changes from “build the source script” to “acquire the pinned supplier script.” The outputs still say doctor; where the overlay is applied determines which outputs receive the replacement.

  • At the Definition level: the default catalog stack is the base catalog followed by the overlay. Both example outputs use that stack, so both resolve doctor to the supplier recipe.
  • At the output level: only tools gets the base-plus-overlay stack. diagnostics continues to use the default source recipe.
  • By changing component selection: diagnostics selects doctor-alt instead. This chooses a different component name from the base catalog; it does not replace the recipe behind doctor.
Compare each independent variant with the same baseline. “Changed” refers to output Build Digests.

Run those comparisons

Use Linux or macOS with Bash 3.2+, Git, jq, GNU timeout or gtimeout, and sha256sum or shasum. Build the CLI in the setup step. The lab needs no network or Docker afterward.

Complete runnable command · from the repository root
bash docs/examples/authoring-lab/run.sh \
  --nkdctl bin/nkdctl --work .nkd/authoring-lab-01

Choose a new workspace for each run; existing directories are refused. Omit --work to use a new temporary directory whose path is printed. The lab creates isolated Git commits and tags, writes fixture pins through the public catalog commands and compiles complete Definitions.

Expected report · printed output, not commands to run
source-pin: changed Build Digests: cli-amd64, cli-arm64, controller, controller-chart
whole-producer: changed Build Digests: diagnostics, tools
output-catalog: changed Build Digests: tools
output-selection: changed Build Digests: diagnostics

Read the last three lines against the table: whole-producer is the Definition-level overlay; output-catalog is the overlay on tools alone; output-selection changes diagnostics to doctor-alt. The separate source-pin scenario updates the derived app source and changes the four listed app outputs.

Read the files that prove the difference

These are exact paths beneath the workspace printed by the lab. The JSON Definitions are complete authored inputs; the saved Plans are complete run plan --json outputs.

  • supplier.json — the complete overlay replacing doctor, bound to the exact base-catalog digest.
  • whole-producer.json and output-catalog.json — compare where the same overlay is selected: the Definition’s default stack or only the tools output.
  • output-selection.json — find doctor-alt in the diagnostics output’s component list.
  • plans/baseline.json and plans/whole-producer.json — load them in the explorer to see source-build operations become supplier-acquisition operations.
  • identity-report.json — read the complete before/after Build Digests for all seven outputs.

The lab finishes by changing the source pin and rejecting the now-stale overlay. That rejection matters: a replacement reviewed against one catalog snapshot cannot silently apply to a changed base.

Follow the links

What you should see

  • Native complete graphs join producer instructions, operations, artifacts, required slots and publication routes.
  • run generate --check reports the scratch bundle is current.
  • run diff reports no change between the exported and generated Plans.
A graph describes intended work. A requested pipeline-attested lane or planned verification node does not prove execution, a signature or qualification. Each named output still needs its own observations and evidence.

Follow the artifact and its evidence

What you should see

  • 34 outputs and 60 evidence records in the complete metadata view.
  • Each disk focus displays 1 of 34 outputs with 11 evidence memberships.
  • The inspection label says payloads, signatures and policy are unverified.
Metadata inspection leaves payload bytes unverified. PR #108 reads the index, manifests, configs and bounded evidence; it does not download image layers, executable archives or QCOW2 bytes. Disk build-provenance-v1 evidence is not a full native disk SBOM.
Native focus, Mermaid export and an offline metadata layout

Every native browse call checks the complete metadata closure before filtering. Focus and Mermaid export repeat that metadata read; use a saved layout for repeated offline views.

Exact output name · metadata scope
bash demos/demo-team-release.sh --reference "$RELEASE_REF" \
  --output nke-node-image-arm64 --mermaid

# Replace the layout path with your saved full or metadata-only OCI layout.
bash demos/demo-team-release.sh --reference "$RELEASE_REF" \
  --layout /path/to/release-metadata-layout \
  --output nke-node-image-arm64 --mermaid

Load exported release-view.json into the HTML explorer. Native Mermaid output needs a compatible renderer. A local layout derives registry locators from the supplied reference without claiming those locations are currently available online.

Three questions. Three different checks.

QuestionWhat answers itPractical limit
What is declared?release browse validates metadata and evidence memberships.Payloads, signatures and policy remain unverified.
Did this workflow complete?The provider result and finalized Run record bind expected and observed outputs.A successful pipeline is distinct from an independent consumer decision.
Can this consumer accept it?release verify applies an explicit identity, issuer, lane and scope.Accepted scope determines the claim; stronger unavailable scopes fail closed.
Optional Linux consumer-policy verification

Use an existing digest-pinned, statically linked cosign binary and policy values your team has accepted. The candidate used a branch identity. Do not broaden a default-branch policy merely to make the candidate pass.

Explicit accepted policy · separate from metadata inspection
"${NKDCTL_BIN:-bin/nkdctl}" release verify --reference "$RELEASE_REF" \
  --lane pipeline-attested --scope artifact-publication \
  --identity "$ACCEPTED_BUILD_IDENTITY_REGEXP" --issuer "$ACCEPTED_OIDC_ISSUER" \
  --cosign "$COSIGN_PATH" --cosign-digest "$COSIGN_DIGEST"

This scope authenticates signed production evidence and exact published contents. It does not establish qualified reproduction, full release qualification/revocation acceptance or deployment readiness. Independent consumer verification was not exercised by this walkthrough.
